### 日常检查与恢复

```sh
systemctl status ninda-backup.timer ninda-file-sync.timer
systemctl show ninda-backup.service ninda-file-sync.service -p Result -p ExecMainStatus
journalctl -u ninda-backup.service -u ninda-file-sync.service --since today
```

手工完整备份使用 `bash /opt/ninda-platform/deploy/backup.sh --wait`。新格式备份隔离恢复检查使用 `bash /opt/ninda-platform/deploy/verify-backup.sh /opt/ninda-platform/backups/<时间戳>.tar.enc`；同时需要同名 `.sha256` 文件及受保护的原 `secrets/backup.key`。检查程序不会连接生产库写数据，而是在无网络临时库执行恢复；确保服务器有足够临时空间及内存。

新格式 `ninda-rds-full-v2` 含 `database.dump`、清单、上传文件、生产配置、必要密钥、当前静态发布目录、Nginx / TLS 和相关 systemd 配置的加密归档。数据库为一致的 `pg_dump` 快照；上传目录是备份时间窗口内的文件副本，不声称数据库与后续并发文件写入具有跨系统原子性。重大变更前仍须停写完成备份。恢复验证会恢复数据库和校验整个压缩流，但不逐项核对数据库内所有文件引用；临时验证数据库容量为 384 MiB、容器内存 512 MiB，数据增长时需先扩展隔离验证容量。解密恢复配置时先使用仅管理员可读的隔离目录，禁止直接覆盖线上路径。密钥的独立受控副本已在本机与服务器比对一致，仍须妥善保留；只拥有加密归档而丢失原密钥无法恢复。

当前 API 镜像另存于 OSS `system-files/releases/20261113-pricing-reference-v1/api-image.tar.gz`，配有 `manifest.json`，300,514,463 字节，压缩包 SHA-256 为 `f3a74473a6b031c609c0635790d6356a35e754d47da2970f96fbbb8492e03a43`；已完整读回。恢复时先校验摘要，`gzip -dc` 后交给 `docker load`，核对镜像 ID `sha256:643e0aa2d79fad98071c28294dae4a294be8fb828db45c252a762e3bba040b62`，再按恢复的 Compose / 私有配置启动。云盘快照、OSS 归档和 Git 中的源码共同提供恢复材料；后续发布也需留存匹配镜像和版本清单。

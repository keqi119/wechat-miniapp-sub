## 3. 七模块录入及开单顺序（旧合作依赖仅供当前实现排查）

下列第 2–4 步及合作草稿前置是当前旧实现参考，已由 v2.2 目标覆盖；不能继续要求合作商完成客户身份绑定。目标允许保存待补合作草稿，但仍须真实材料、相应业务版本及独立复核后才可用于新订单。其他模块门禁继续保留。

七个模块保留独立入口，业务按以下依赖顺序准备。车辆、主体、产品及保单的基础资料可以先录入草稿；合作档案创建已要求通过车辆权属审核，分润规则即使草稿也要求有效的已归档合作版本及完整条款。不能用提前建草稿绕过这些前置条件。

1. **车辆管理**：先建车型及车辆草稿，录入真实 VIN、车况、里程、所在地与照片。VIN 按去除首尾空白、转大写校验 17 位有效字符和唯一性；缺 VIN 或冲突先由运营核实，不创建第二条档案绕过。
2. **合作商管理**：选择企业或个人主体，录入资料、上传准入和本人／经办关系材料，分别提交独立审核；对每辆车提交并审核权属绑定。合作商资料或绑定发生变化，应按当前版本重审。
3. **合同管理中的合作协议**：使用已审定模板生成打印稿，线下签署，按要求上传完整页、页序、签字及盖章原件，提交另一名有权限员工复核。协议须覆盖本车及实际租期。合作授权只证明约定范围内合作，不替代客户逐单租赁合同。
4. **合作商财务约定**：在当前已归档合作协议范围内建立分润规则及收款账户，按权限独立审核。首版为“约定规则＋人工对账结算”，不自动分账，不因录入收款账户就执行银行付款。
5. **产品管理**：建立说明型或次数型权益及版本，再组合基础订阅和权益，设置适用车辆／车型、价格、期限和条件。运营核对后发布产品版本并上架车辆；草稿和停用版本不能作为新的可售方案。旧文本权益不得根据“若干次”等文案自动生成次数余额。
6. **保单管理**：先配置车型保障要求及适用产品的补充要求，再录入保单、被保车辆、险种、金额、免赔与除外条款、保障区间及原件。独立复核人逐车、逐要求核验；续保、批改、退保使用对应版本，查看续保提醒并处理，不用旧保单覆盖已移除车辆或已经过期的保障。
7. **客户及订单管理**：客户资料、必要授权及资格有效后，受理申请；生成候选方案并完成风控审核。候选方案生成不立即通知客户确认，只有通过审核的当前方案可供确认。客户确认后建立订单及逐单线下合同档案；合同资料通过独立复核且无未解决反馈后，按账单支付，再办理交车。

第 7 步涉及客户管理和订单管理；以上第 3 步及订单内合同都统一沉淀到合同管理模块。合作商、产品、保单是车辆可售与实际交车的共同条件，不能只凭车辆“已上架”状态判断已具备履约资格。

所有金额以整数分入库，页面按元展示。报价、收入分润、权益和合同形成各自版本；调整既有订单应走订单条款变更流程，不覆盖历史快照。

## 4. 线下签署、独立复核和资料反馈

合作协议目标支持登记既有真实签署原件，不要求重新打印重签。下文合作商自行提交反馈的描述属于当前旧接口；v2.2 关闭其业务写入，改由运营根据电话或线下沟通记录及处理。客户资料反馈和全部历史未关闭反馈的业务约束保持。

档案覆盖合作协议、租赁合同、交车单、还车单及解约文件。标准操作为：创建当前业务版本 → 生成打印稿 → 线下真实签署 → 上传完整原件并排好页序 → 提交 → 独立审核 → 归档。先有正式模板和业务快照，再处理扫描原件；不要把任意附件当成已经签署的合同。

提交人、材料上传人不得复核本人材料。复核人检查主体、车辆、期限、金额、业务版本、必需签署方、签字盖章及页完整性，拒绝时说明需要补齐的具体事项。修改后重新提交；已归档历史版本不原地改写。

客户或合作商对资料提出反馈后，由运营核实并办理更正及反馈关闭。按当前阶段，未关闭反馈会阻断付款、交车、合同变更、结算或关单；不能只修改展示文字或数据库标记解除阻断。合作协议反馈还会影响其覆盖的相关订单。

当前业务变更导致版本不一致时，页面会保留已填内容并提示刷新。确认新版本后再提交新的意图；同一操作网络重试沿用同一个幂等键。不要连续点击、换账号或手工改版本号强行提交。

## 5. 账单支付、异常到账及人工结算

合作商结算、收款账户、付款登记及核对的目标经办/复核岗位已改为获授对应权限的运营，须不同实际人员办理；下文 ADMIN/FINANCE 是当前实现的角色限制参考，不要求为新合作流程另设 FINANCE。客户支付、退款和异常到账专用权限及渠道事实门禁不随此调整放宽。

客户只支付当前可支付账单。正常付款由经验证的渠道通知、账单归属、金额和交易号共同判定；前端返回“支付成功”不是独立履约依据。

工作台提供异常到账入口，支付列表支持 `reconciliationRequired=true`。存在该标记时，即使渠道记录为成功，仍按“到账待核对”处理，不能据此开始交车或认为合同已履行。

ADMIN 或 FINANCE 打开付款详情，核对原账单、订单、金额、渠道交易号、当前合同和退款记录，上传核对依据，选择处理方式并提交。另一名有权限且不是提交人、附件上传人的员工复核。核对记录有独立编号及 `SUBMITTED / APPROVED / REJECTED` 状态。

| 核对方式 | 适用条件与结果 |
| --- | --- |
| `APPLY_TO_BILL` 计入原账单 | 仅押金、订阅账单支持此方式；在原金额、交易号、原账单、当前合同等条件重新校验且没有退款冲突后，通过独立复核计入原账单。里程等其他收费须按完整原路退款核对处理，不能用清标记冒充权益已发放。不能借核对转付其他账单或修改渠道交易事实 |
| `REFUNDED` 已退款核对 | 仅在完整退款事实已成立时核对关闭异常；不产生自动履约，也不在核对动作中发起外部退款 |

退款申请、审批和渠道退款执行仍走专用退款流程。核对被拒绝或原始事实不齐时，保留异常标记和完整记录，补齐后重新申请；不能用手改 `paidAmount` 或清除标记代替复核。

合作商结算按已批准的规则版本和收入来源生成，人工核对后审批。线下真实付款完成后登记凭证，再由独立人员核对；登记付款并不等于系统已向银行发起支付。不可把核对金额直接写成已付来凑平账。

## 6. FIELD 交车与还车

外勤从服务号“员工工作台”进入，仅能打开本人当前任务。运营负责创建、分配或重新分配任务，外勤按页面采集必填照片、里程、车况和查验项。重新派单后原外勤不能继续操作该任务或下载受保护文件。

交车时，先确认订单合同、账单、合作及保障检查通过，再按现场事实完成查验并发布供客户确认；办理纸质签收单，使用任务内专用上传及提交入口。客户确认和纸质签收单独立复核是分别要求，任一步未完成不得强制完成交车。文件下载走本人任务范围校验，不能转发通用存储地址。

还车时，外勤记录实际收车时间和现场事实，完成查验、纸质还车单及提交。**实际收车登记不等于订单已正式还车、结算完成或允许立即重新上架。** 实际收车后的计费和服务限制由后端执行；运营继续处理交接确认、还车单独立复核、用量与费用结算、退款及关单。不得为了提前关单填写虚假的收车时间或绕过客户确认。

照片或纸质单上传失败时保留任务及已填写内容，核对网络和文件类型后重试；版本冲突先刷新当前任务，再核对现场事实。任务不属于本人或账号权限不足时联系运营重新派发，不借用其他员工账号。

## 7. 旧数据检查与受控回填

源码入口为 `apps/api/src/operations/seven-module-migration.ts`，导出：

- `inspectSevenModuleMigration(tx, at)`：只读提取当前业务事实，返回计数和管理员缺项清单。
- `auditSevenModuleFacts(facts, at)`：对已提取事实进行纯计算，可用于不连接数据库的规则测试。
- `runSevenModuleBackfill({apply:false})`：默认预演，在数据库只读事务内检查。
- `applySevenModuleMigration()`：使用严格校验后自行创建的测试库连接，事务内调用已有 `migrateLegacyProducts(tx)`，输出迁移前后清单。

检查输出只包含业务 ID、固定缺项代码、数量和检查时间，不输出 VIN 值、姓名、证件、地址、手机号、保单正文、密钥或收款账户。清单仍属于内部业务信息，应保存在受控位置。

| 缺项代码 | 管理员处理 |
| --- | --- |
| `VIN_MISSING / VIN_INVALID / VIN_DUPLICATE` | 核验原始车辆材料，补齐或纠正当前档案；重复项按业务 ID 定位，报告不展示 VIN |
| `OWNER_BUSINESS_UNVERIFIED` | 当前旧实现还关联本人／经办关系；仅用于定位现网限制，不继续要求客户账户注册。v2.2 改为依据纸质合作资料的独立复核；实质主体变化不能继承旧审核，手机号访问变更不使业务失效 |
| `OWNER_VEHICLE_REQUIRED` | 核对并独立审核当前车辆权属绑定 |
| `OWNER_COOPERATION_REQUIRED / OWNER_COOPERATION_FEEDBACK_OPEN` | 补齐当前车辆范围和有效期的归档合作协议，或处理未关闭反馈 |
| `PRODUCT_VERSION_MISSING` | 旧套餐待回填或车辆尚未配置产品；回填后仍须人工核对、发布 |
| `PRODUCT_REVIEW_REQUIRED` | 当前产品版本未发布；确认完整业务条件后通过业务流程发布 |
| `INSURANCE_REQUIREMENTS_*` | 配置当前车型及适用产品的保障要求；报告不会生成要求或替代业务审核 |
| `INSURANCE_POLICY_* / INSURANCE_REQUIREMENT_UNVERIFIED / INSURANCE_VEHICLE_REMOVED` | 补齐当前有效保单、续保或批改，并按当前要求逐车核验 |

保单待办在 API 成功启动后扫描一次，此后每小时扫描，按北京时间生成 30／7／0 天提醒；站内待办持久去重，扫描失败下轮重试，不自动发送外部短信。

检查是指定时点的库存盘点，不代表某笔未来订单已通过完整租期校验，也不替代订单支付及交车时的实时门禁。

回填的唯一业务变更是：每条未关联产品版本的旧逐车套餐创建独立产品及版本；即使同名也不合并；生成 `DRAFT`，旧套餐改为 `active=false`；文本权益转为 `DESCRIPTION`，数量和单位为空，保留原文供人工核对。第二次执行不再为已关联套餐新增记录。不会自动发布、建立次数余额、修改历史订单快照或 ESIGN 模式，也不会生成准入、权属、合作协议或保单审核事实。

### 测试库执行流程

只允许本项目 `scripts/run-mvp-api-tests.mjs` 安全执行器启动 CLI，数据库必须同时满足：`NODE_ENV=test`，`DATABASE_URL` 与 `TEST_DATABASE_URL` 一致，PostgreSQL loopback 地址、端口 `55432`、数据库 `chundian_test`；额外连接参数只允许 `schema=public`。CLI 还验证安全执行器锁的父进程身份，拒绝直接启动或并行占用。不在命令行传递连接凭据。

由主控配置受控环境变量并确保测试窗口可用后，从仓库根目录执行：

```powershell
node scripts/run-mvp-api-tests.mjs --migrate
node scripts/run-mvp-api-tests.mjs test/seven-module-migration.test.ts
node scripts/run-mvp-api-tests.mjs --backfill-dry-run
```

执行器预演入口 `--backfill-dry-run` 映射到 `src/operations/seven-module-migration.ts --test`；实际回填入口 `--backfill` 映射到 `src/operations/seven-module-migration.ts --test --apply`。先通过执行器预演并核对待办，再执行受控测试回填：

```powershell
node scripts/run-mvp-api-tests.mjs --backfill
```

执行器与回填源码须来自同一版本，不直接绕过 runner 调用 TS 脚本。回填输出 `DRY_RUN` 或 `APPLIED` 以及迁移前后计数；失败时整笔事务回滚，不保留半套产品。日志只显示固定安全错误，数据库详情在受控测试环境中检查，不复制原始 ORM 错误到公开渠道。

真实数据库测试在事务内建立两条同名旧套餐和文本权益，验证各自草稿、旧套餐停用、权益无猜测次数、重复执行零新增、历史订单及合同未改变、没有伪造审核和保单；测试末尾回滚合成数据及本次测试回填。

### 生产处理边界

本脚本**不允许生产数据库**，不能把连接检查改宽或把生产库改名为测试库来运行。生产兼容处理须另行准备只读盘点、业务补录清单、备份及恢复演练、明确范围、负责人和独立发布窗口，经主控核对后使用专门审阅的发布步骤。此手册没有授权或声称已执行生产回填。

## 8. 异常处置和回滚

| 场景 | 处理方式 |
| --- | --- |
| 版本冲突 409 | 保留表单内容，重新读取当前版本，核对变化后重新提交；同一请求的重试继续使用原幂等键，不绕过版本控制 |
| 缺准入、权属、合作文件、保障或正式模板 | 按缺项进入对应模块补齐真实资料并独立审核；不造数据解锁 |
| 字体缺失或打印失败 | 修复受控字体路径、权限和字体可用性，再检查实际 PDF；不输出空白、乱码或缺页文件作为签署稿 |
| 异常到账、金额或交易号不符 | 保留待核对状态，按双人核对流程办理；不将渠道成功直接解释为可交车 |
| 档案错页、漏签、反馈未处理 | 新建／修订对应资料版本、重新签署或补齐原件后复核；保留旧版本和反馈记录 |
| 错单、旧方案或已归档文件需作废 | 先核对订单、文件类型、模板及方案版本；未通过的资料退回补件，已归档资料通过有权限的更正／作废流程保留原档和原因。旧档不能作为新版本收款或交车条件，不直接删除文件或修改数据库状态 |
| 人员离岗或岗位调整 | 管理员停用账号或调整角色，使旧会话失效；核对并重新派发未完成交还车任务。原上传、审核和财务记录保留原操作人，不能由同一人接替后自审 |
| 实际收车已登记、正式还车待核验 | 保留实际时间和查验原件，补齐客户确认、纸质单及独立审核；停止新增用车权益的购买，继续处理待结账单。不能撤销收车事实来恢复在租，也不能提前标记已结清 |
| 退款结果未知或回调迟到 | 保留原退款单、原渠道请求标识与待核验状态，先查询渠道并核对可信回调；未知不当作失败，不创建第二笔替代退款。确认结果后按独立复核及幂等流程继续，未核清前不关单 |
| 归档库中的历史签署需查询／恢复 | 当前新库不含旧业务；先核对归档清单、订单和原签署模式，由主控确定兼容查询或受控恢复范围。旧库不用于开发测试，不将旧订单导入为 OFFLINE，不重新发起签章冒充恢复 |
| 回填失败 | 当前回填事务整体回滚；排查结构或数据问题后重新预演，再按同一受控入口执行 |
| 已回填产品有误 | 通过产品草稿和后续版本更正；不批量重新激活旧套餐，不删除已经被引用的历史版本 |
| 发布需回滚 | 先控制新申请及履约操作，核对代码、配置与数据库结构兼容性及恢复点，再在独立窗口处理；财务和审计事实通过受控更正保留，不直接删表或改账 |

任何异常或回滚都不得把新订单切回 ESIGN、打开新电子签请求、退回 Mock 页面或使用假成功响应。历史 ESIGN 记录继续按其原模式保留，不能为了新业务开通而批量修改。

2026-10-27 首次生产切换已按用户决定建立空业务库，原库隔离归档并加密备份。后续补丁只使用 `deploy/ninda/activate-mvp-release.sh` 的 preserve 模式，不能重复 fresh。发布入口先控制写入并停止 API，再备份及实际恢复到隔离验证库；迁移开始后的失败保持维护，修复或受控恢复完成前不启动不兼容旧镜像。实际回执、版本和恢复点见 [生产发布记录](../evidence/ninda-seven-module-release.md)。

# V31 Task5 initial subscription integration

New-route rollout requires **both** `NEW_ORDER_CONTRACT_MODE=ELECTRONIC` and `CUSTOMER_IDENTITY_POLICY=SIGNING_REQUIRED`. Task11 owns the controlled environment switch and validation; this task preserves existing absent-setting defaults. Real provider/payment/signature actions remain disabled in local tests.

`POST /admin/applications/:id/final-plan` uses the existing staff, order/application lock, revision and idempotency guards. ELECTRONIC candidates are `DRAFT`, require the current published product/listing and effective electronic lessor/cooperation sources, and stay invisible to customers until ordinary risk approval. `months` must exactly equal the selected published product version's actual `months`, and satisfy `actualMonths >= minimumTermMonths >= 3`. Actual and minimum months are independent version fields; the quote cannot choose a different duration. A different actual duration requires selecting an appropriate published product version. The product's original configuration/version remains unchanged. ELECTRONIC accepts `commercialTerms` containing exactly `vehicleIdentification`, `customerAddress`, `handoverArrangement`: these are per-order facts; fixed V31 legal paragraphs belong in the approved template. `startDate` is the **planned delivery day**, never evidence of actual service. `firstDueDate` must be omitted on this new route. The server uses the planned day for the first prepayment due date.

ELECTRONIC defaults expose those three factual fields plus `agreedFeeComponents: {baseFeeAmount, mileageMonthlyFeeAmount}` in integer cents. A changed monthly total requires the existing explicit `priceAdjustmentReason` and genuine agreed components whose sum equals `monthlyFeeAmount`; no proportional or duplicated standard fallback is inferred. These components persist separately from immutable `productSnapshot`, appear in application DTOs, participate in commercial/source hashing and drive the private 01 renderer. This retains only the existing supported price-adjustment path and does not add arbitrary bargaining or duration editing. Task6 must compare agreed components with actual auto-sign scope; Task10 mounts these fields, planned date/place/contact facts and existing contact address without exposing redundant legacy legal prose.

Customer confirmation rechecks the full current product/risk/lessor/revenue sources and explicit owner-data consent, then freezes CUSTOMER, actual OWNER and actual PLATFORM database subject IDs. It creates one first-rent prepayment bill and a deposit bill when required. Future subscription bills and actual usage periods do not exist before delivery. Prepayment has no claimed performed service dates. `ElectronicPreparationService.prepareSubscription(orderId, revision, actorId, idempotencyKey)` delegates to the authorized V31 preparation workflow; existing `/admin/electronic-documents/prepare` remains the HTTP entrypoint.

Full three-party provider-verified signature/file/archive proof advances to `AWAITING_PAYMENT`, never ACTIVE service. `readElectronicSubscriptionReady` separately exposes `legalSigningStatus` and `filingStatus` while final archive is pending: a true signed result with archive failure must be retried as archival, never shown as requiring another signature. Bill publication and payment require authoritative current electronic archive proof. Future-month publication/payment is blocked before actual service anchor exists.

`POST /admin/orders/:id/recheck-delivery` now supports ELECTRONIC under the existing guards and authoritative contract/funding/business checks. The server process projection uses electronic proof and no paper upload/review, independent handover-signature or planned/actual date-amendment gate on this route. Completed handovers remain immutable history.

All new ELECTRONIC handovers use `ONLINE_RECORD`, approved current terms, exact current evidence versions and actual Fadada identity for customer confirmation. The legacy sign endpoint rejects this mode. Actual completion runs the existing transaction and current staff/RBAC/ownership/revision/idempotency gates; it rechecks insurance at the actual instant, driving qualification, customer identity, current actual lessor/binding/cooperation and authorization scope covering the full actual service range. A source/scope gap blocks completion; a date difference alone does not require another signature.

Existing future unpaid draft bills can be re-dated; any existing future money facts require manual review. The existing completed assignment, initial service-stage snapshot, bill schedule and benefit grant are then created in the same delivery transaction. The PDF, commercial hash, planned day and signed snapshot never change for delivery delay. Replayed completion or an authorized replacement operator does not create another account/stage/bill/grant.

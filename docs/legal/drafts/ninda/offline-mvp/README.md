# 宁达线下纸质合同模板审阅包

状态：**DRAFT_PENDING_USER_REVIEW**。草稿版本：2026-10-27。平台服务方：上海宁达信息科技有限公司。联系邮箱：like@ndacar.com。

本包是供业务负责人审阅的文本草稿和接口格式样本，未获用户正式审定，未经过律师审阅，不代表已发布、已签署或已归档。没有创建生产法律文档、业务记录、支付或签章任务。所有 JSON 的 `legalDocumentDraftPayload` 均省略 `confirmedBy`、`confirmedAt`；不能把草稿状态标记改成已批准代替真实确认。

本轮按照已确认的七模块线下方案起草。租赁合同与终止文件为客户、实际出租方、宁达三方；合作协议为企业或个人合作商与宁达双方；交还车单按当前实现采用客户与宁达作业方双方，是否要求出租方加签列入下方审阅事项。平台服务方不因代收或现场作业成为车辆出租方。

## 一、文件与系统映射

每份 `.md` 提供易读正文；同名 `.template.json` 中的 `legalDocumentDraftPayload` 使用实际管理 API 字段，`content` 是含 `body` 和 `requiredSigners` 的 JSON **字符串**。外层审阅元数据不是 API 请求字段。草稿标记写入正文，正式版本需在明确审定后另行制作及核对摘要。

| 审阅正文 | 档案 kind | subjectType / subjectId | LegalDocument.type | 本包必签方 |
| --- | --- | --- | --- | --- |
| [合作协议](owner-cooperation.md) | OWNER_COOPERATION | OWNER / 合作商 ID | OFFLINE_OWNER_COOPERATION | OWNER、PLATFORM |
| [三方租赁合同](rental.md) | RENTAL | ORDER / 当前线下订单 ID | OFFLINE_RENTAL | CUSTOMER、OWNER、PLATFORM |
| [交车确认单](delivery-receipt.md) | DELIVERY_RECEIPT | HANDOVER / 当前交车记录 ID | OFFLINE_DELIVERY_RECEIPT | CUSTOMER、PLATFORM |
| [还车确认单](return-receipt.md) | RETURN_RECEIPT | HANDOVER / 当前还车记录 ID | OFFLINE_RETURN_RECEIPT | CUSTOMER、PLATFORM |
| [三方终止协议](termination.md) | TERMINATION | ORDER / 当前线下订单 ID | OFFLINE_TERMINATION | CUSTOMER、OWNER、PLATFORM |

JSON 中 `version: 1` 是候选版本，不证明生产尚无同类文档。正式制版前须读取目标环境各 type 的现有版本，决定新的不可变版本号。合作协议创建档案时另传 `scope: { vehicleIds, validFrom, validUntil }`；该 scope 属于实际合作资料，未在本包预填。

管理 API 为 `POST /api/admin/legal-documents`；仅在实际审定信息齐备后才可能通过 `POST /api/admin/legal-documents/:id/publish` 发布。档案创建为 `POST /api/admin/offline-archives`，打印为 `POST /api/admin/offline-archives/:id/versions/:versionId/prepare`。本包不执行这些操作。

## 二、打印器能力与本包用法

依据 `apps/api/src/offline-documents/print.ts`，当前仅识别以下变量：

| 变量 | 实际来源与可用范围 |
| --- | --- |
| `{{customerName}}` | 冻结 CUSTOMER 名称；合作协议无客户，不使用 |
| `{{ownerName}}`、`{{lessorName}}` | 冻结 OWNER 名称，企业与个人均适用 |
| `{{platformName}}`、`{{platformLegalEntityName}}` | 冻结 PLATFORM 名称；应核对为上海宁达信息科技有限公司 |
| `{{contractNumber}}` | 档案版本的合同编号；未录入时使用档案 ID。不是关联主合同号或订单号 |
| `{{monthlyFee}}`、`{{deposit}}`、`{{termMonths}}`、`{{startDate}}`、`{{vehicleIdentification}}` | 订单商业快照；不保证在 OWNER、HANDOVER 上下文存在，因此本包正文不使用这些变量 |

本包只使用主体名称和当前文书编号。旧文案中的 `contractNo`、`orderNo`、`templateVersion`、`lessorCreditCode`、`staffName`、`readingKm`、`manifestHash` 等不是此打印器的变量，不能直接粘贴旧模板。自动替换后仍有双花括号时，打印器拒绝生成。

打印器已自动附加：签署主体、可用的订阅方案、车辆与服务约定、合作车辆档案 ID 及有效期、交接事实、约定权益附件、冻结的用量政策内容，以及相应签字区。本包不硬编码月费、押金、里程、分润比例、违约费用、付款账号或当事人身份。用量政策附件若仍含历史加购、换车或未使用权益处理条款，须核对其是否确为本单已确认内容；不能仅因旧文案发布过就纳入新单。

**当前打印边界须如实处理：**

1. OWNER 合作协议自动部分仅有车辆档案 ID 和有效期，没有可读车牌/VIN、分润比例、结算周期、收款对象版本或合作服务费用。必须附各方确认的《合作车辆与服务范围清单》《分润与人工结算约定》。先把真实约定随合作协议签署归档，再据此建立系统规则；不能要求尚未建立的系统规则反过来证明协议已签。
2. HANDOVER 自动部分只有实际时间、读数和当前 checklist 条目，不自动完整列出车辆标识、地点、电量、物品、照片文件清单、现场经办人、客户异议及处理期限。逐单核查 checklist 和查验附件是否覆盖这些信息，未覆盖的须形成随同签署、上传的事实清单。正文没有声称这些字段已自动打印齐全。
3. TERMINATION 当前沿用订单商业快照，不自动生成终止生效时间、租金截止、差额、应退项目或结算期限。须另有三方签署的《终止事项及结算明细》，并与后续真实账单/退款记录关联。原订阅方案不是最终终止结算单。
4. 当前交还车打印签字区取 `context.requiredSigners`，默认 CUSTOMER、PLATFORM；档案版本可从模板增加 OWNER，但打印器未据此增加 OWNER 签字框。若业务决定三方均须签交还车单，须先解决打印与必签方一致性并复核，不能只改模板数组。
5. 纸质附件和扫描件由实际人员上传，系统不自动把上述人工附件纳入打印 PDF，也不自动验证纸面签章真伪。审核必须逐页核对；“已审核归档”只表示材料通过人工复核，不表示付款、交付或退款完成。

## 四、正式审定与逐单材料的区别

与此前正式租赁 v2 的主要变化是：由出租方与客户的双方法律正文调整为出租方、客户、宁达三方纸质文件；允许真实出租方为企业或个人；去除新电子签、电子章和自动用印流程，增加纸质附件、原件保管及独立复核；分润另在合作协议附件中明确。除前表显式列出的待定事项，不能因为模板改版推定旧价格、权益、退款或责任约定失效。历史电子签订单继续使用其原有文件及模式，本包不用于批量替换。

先确定上表的模板级选择，形成可逐字审阅的正式候选正文、附件格式和实际版本号，记录真实确认人、确认时间及完整内容摘要。不得在未审定草稿上补一个批准字段直接发布；历史双方法律文案、企业电子用印授权、里程规则的批准均不等于本包的三方线下文本获批。

正式模板获批后，具体合作商/客户、车辆范围、金额、期限和履约事实仍须逐单从当前冻结资料取得。打印前登记文书编号，核对正文、自动附件及所需人工附件；发生实质变更时生成新版本并重新确认，不能在扫描件中单方面改价或改主体。上传人或提交人不能审核自己参与的资料。

主文来源与兼容性核对见 `review-manifest.json`。本包未添加法律条文引述、处罚比例、银行资料或自动电子签/自动扣款/自动分账承诺。

# 宁达上线入口一致性修复计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development；按分配文件实施，主控统一集成与发布。

**Goal:** 让车辆可申请资格与合作准入一致，让线下模式的小程序普通入口不再依赖电子签流程。

**Architecture:** 沿用已有合作、协议、规则门禁，提取可供目录使用的只读判断；申请提交在事务内再次检查。沿用公共签署配置返回明确业务能力，客户端按服务端能力隔离新电子签和历史资料。

**Tech Stack:** 现有 NestJS、Prisma/PostgreSQL、原生微信小程序；无新依赖、表或迁移。

**Spec:** [七模块基线](../specs/2026-10-27-ninda-seven-module-mvp-design.md)、[线下签署基线](../specs/2026-10-26-ninda-offline-contract-mvp-design.md)。本计划修复已批准行为的遗漏，不新增业务范围。

## 全局约束

- 仅写本项目，保留全部现有业务记录、历史电子签文件和用户新录入数据，不重跑清库切换。
- API 数据库测试只允许 loopback:55432/chundian_test，同一时刻一个进程，使用 scripts/run-mvp-api-tests.mjs。
- 不执行真实支付、退款、实名、签章或人工业务审批；不改生产凭证和业务开关。
- 保留黄黑视觉及小程序 1.1.3 登录恢复保护；历史对象按冻结模式展示。
- 不提交或推送脏工作树。新发布基于已上线静态抽屉版本与 API v6 的冻结源码，防止 UI 回退。

## 重点边界

1. 车辆已被运营上架而合作资料缺失：保留上架事实，公开为暂不可申请，提交也必须拒绝。
2. 申请还没有实际起租日：采用现有北京时间当前日及所选产品租期做预检，不写成合同起租日；真实方案整租期复核保留。
3. 合作主体、车辆范围、归档版本或分润规则在浏览后失效：事务提交再次判断，错误不泄露内部身份和财务信息。
4. 设备带旧签署缓存或深链：OFFLINE 普通恢复不调用供应商、不展示供应商 URL；支付恢复独立保留。
5. 配置缺失、接口失败或旧会话失效：仅关闭新电子签办理，公开协议与正常登录仍可使用，不冒充新会话成功。

# 三端正式电子签切换实施计划

> 执行方式：superpowers:executing-plans；本轮用户已明确授权施工和上线，沿用已批准 V3.1 方案，不重复请求工程许可。使用项目内隔离候选目录，最终由独立审阅者核对变更。

**Goal:** 新增正式订单及其 V3.1 合同全部使用电子签，小程序、公众号原企业 H5、admin 无线下签署办理通道。

**Architecture:** 复用统一 ElectronicSigningTask 和既有生命周期命令，补齐前端与正式模式接入；只在核验发布包、持久化身份/印章、模板及旧版本影响后切换 ELECTRONIC / SIGNING_REQUIRED。企业逐份本人电子签继续可用，未经渠道核定不启用自动盖章。

**Tech Stack:** NestJS / Prisma / PostgreSQL、React / Vite、原生微信小程序。

**Spec:** docs/superpowers/specs/2026-11-07-ninda-v31-contract-autofill-design.md；补充依据为 2026-11-10 用户本轮正式全流程切换指令。

## 全局约束

- 本轮实际验收证明 01、02 主文、02 独立授权的真实签署归档；03—06 不冒称已真人验收。
- 金额整数分、后台 RBAC、客户归属、三方顺序、版本冲突、幂等、可信回调/查询及最终文件校验不变。
- 保留既有实名/证书/印章、真实合同/付款及历史来源，不执行业务重置或代本人签章。
- 普通交接只留实名线上记录，不新增纸质或电子签交接单。
- 只使用已批准模板。已批准工程方案不伪造尚未核定模板的批准事实；03—06 完整现有样张另提交核定，缺失正文的特殊场景明确阻塞，不回退纸质。
- 延续最新 1.3.2 UI 和已发布广告功能；不增加剪贴板、虚拟验收入口或隐私 API。
- 限本项目及宁达独立部署；旧库旧系统不连接。无关文件不提交、不推送。
- 复杂资金异常沿用证据留存、阻止重复付款、人工复核，不新增财务自动化。

## Review Focus

1. 已实名/已选章跨版本保存，停派或部分签署不能重置/重复派发。
2. 新订单冻结 ELECTRONIC，旧报价不能在切换后新建纸质订单；既有已签/已付款来源仍可读。
3. 03—06 客户待签不再被仅 SUBSCRIPTION 的前端条件隐藏；身份/会话/原文版本变动清除同意。
4. 后台电子订单整体进度不能因旧纸档/权限/实际租期空值而 500；缺资料给可定位原因。
5. 拒绝纸质写入口和缺模板办理；源码包、上线配置和实际三端行为一致。

## 1. 目标与边界

在现有 PC 后台、客户微信小程序、合作商 H5、现场员工入口内完成实名、电子签及自动归档，替换人工合同生成后下载、线下签字、上传签字件、人工审核归档的办理流程。保留既有产品、报价、计费、支付、车辆交接与业务生效规则。

晓浪仅提供现有法大大 API 接入能力。宁达负责业务通知、发起签约、状态核验、调用法大大归档接口及平台档案存储。晓浪不成为合同方、代理人、被授权人、通知接收方或业务档案办理方，也不出现在各环节协议中。

车辆验收、交付、还车及换车交接只保存线上实名操作及证据，不生成待电子签的交接单。浏览车辆仍无需实名。

## 3. 实施路径与取舍

采用“复用当前 API 适配层，统一重建电子合同编排”的路径。这符合用户要求继续利用现有仓库和晓浪所提供 API 能力，不需要另建系统。

| 路径 | 结论与理由 |
| --- | --- |
| 复用 API 适配与安全基础，统一签署任务及业务生效条件 | 采用。保留已有原生微信认证回跳、回调验签、查询绑定和受保护文件能力，覆盖三方及双方协议 |
| 直接启用旧签署开关、保留旧双签流程 | 不采用。现有客户／平台任务及客户／出租方任务均不能直接代表三方完成，新版合作协议和多种订单协议也不能据此生效 |
| 更换法大大产品版本、应用或整套合同系统 | 不作为当前方案。若供应商确认现有应用不能满足主体隔离，只整理必要配置变更及影响后再确认，不擅自改动晓浪旧业务 |

源码复用固定来源为 `453da778dcfefd3727813179382490903644ef26`，以项目已保存的来源清单和当前适配代码为基础；不读取落后旧工作树替代它，不连接旧业务数据库。

这是跨 API、数据、四个入口及发布切换的项目级改造，不是一次页面替换。

## 4. 现有能力与必须核实的渠道限制

### 4.1 已有能力

- 客户个人认证、企业认证、证书／印章查询、个人和企业手动签、自动签请求、查询结果绑定及签后 PDF 下载已有实现。
- 原生小程序 web-view 与人脸认证中间页已有可用接入结构；沿用业务域名白名单及服务端受控回跳，不开放任意链接。
- 合作商 H5 公司管理员当前主要用于查看合作资料；该账号不自动具有法定代表人身份或签署权限。
- 四类交接已经支持线上证据、客户确认和后台实际完成，本轮将实名身份绑定补入该链路。
- 订单中的金额、账单、续期阶段、换车和交接实际事实已经分别存储，不能由一条签约回调替代。

### 4.2 自动盖章限制

2026-10-21 的项目证据记载：`before_authsign.api` 生成的授权函被授权人曾显示晓浪科技；文档中未见自定义被授权主体参数，记录中的供应商修正状态为未解决。这是历史证据，不等同于当前线上配置核验结果。

官方本地接口资料明确：自动签需先取得 `before_authsign.api` 的渠道权限；普通自定义 PDF 签署不能替代该权限。印章授权接口中的被授权账号为个人账号，也不能未经验证当成企业间自动用印方案。

上线前分别验证：

1. 客户、合作商及宁达各自认证账户与实际身份、证书和印章匹配。
2. 认证、服务、授权、签约等实际页面和生成的协议不出现晓浪业务身份；不把“本地显示宁达”当成渠道文件已修正。
3. 自动签授权函、实际权限对象、适用范围和签章对象均满足要求。宁达与合作商各自授权，API 应用密钥不代表任何一方的授权。
4. 宁达业务通知及 provider 回调只进入本项目；供应商必要的本人认证／签署验证通知也不得把晓浪作为业务通知方或接收方。
5. 新配置仅作用于宁达，不改动旧系统应用级权限、默认印章、授权或回调配置。

自动签条件不具备时，新文件使用双方企业逐份确认签署；不得借用晓浪印章、修改实际授权人账号或用本地授权书伪造渠道授权。若手动签或实名页面也无法满足主体隔离，相关发布必须停在核验阶段，列明供应商需解决的配置，不能声称手签自动解决全部主体问题。

现有资料未提供最新渠道配置证明，真实认证、授权及签章需在后续明确验收范围内由有权人员操作。

## 5. 身份、权限与授权范围

### 5.1 三方身份

- 甲方：车辆实际出租合作商；可以是企业或自然人。
- 乙方：本订单客户本人。
- 丙方：上海宁达信息科技有限公司。
- 合作协议只有合作商及宁达两方；不得追加晓浪角色。

个人保留姓名、身份证号、手机号及认证证据；企业保留企业名称、统一社会信用代码、认证证据、证书、印章和有权操作人员关系。敏感字段加密存储和按权限脱敏，前端无权指定任意 provider customer_id 或 seal_id。

复用有效的法大大账号前必须查询核验，不依据旧的本地“已认证”文字直接放行。身份变更后重新核验；已经发出的文件保存原身份和证书快照，不能改绑到新身份。

### 5.2 本方案提出的办理时点

为了保留当前申请习惯，客户可以先登录、填写资料和提交申请；运营继续审核驾驶资格与信用。进入正式电子签前必须完成法大大实名，交接确认时再次核验身份绑定和当前可用状态。实名认证不能替代驾照及业务资格审核。

企业入驻由法定代表人本人完成认证及授权，沿用现有已核验法人路径；普通公司管理员可查看资料，但不能仅凭管理员身份授权用印。首版不扩展未经当前接口验证的代理人认证路径。

### 5.3 企业用印

- 企业授权明确主体、期间和文件种类；合作协议限定适用车辆及业务条款。两者均有效才可执行范围内自动签。
- 订阅、延期、同价／升级换车、续订、终止及取消分别归入明确文件种类；不沿用旧“仅主合同”的授权覆盖新增种类。
- 合作协议本身须合作商确认具体版本。自动签条件已满足时，确认后可按其授权自动用印；未满足时由双方企业本人手签。
- 超出既有合作协议或授权范围时，先确认新的条款／范围并取得相应签署或授权，不能只点后台确认就扩大权限。
- 每次派发前重新检查身份、印章、授权是否有效，车辆归属、冻结交易条件、文件版本和业务审批是否一致。
- 自动签条件在首次派发前不完整时，整份新文件的两家企业均改为手动模式，清晰展示原因。已经发生签署或派发结果未知时，不新建交易号重复签、不把已签事实清空。
- 停用、撤回或过期阻止新的用印请求；已经完成的签章和合同效力事实保留。权限查询本身不得触发签章。

后台管理员的“可自审普通资料”不代表可以替客户或合作商签署，亦不代表可以替企业法人完成授权。资金事项继续独立复核。

## 6. 合同范围、文件和生效

### 6.1 文件矩阵

| 文件 | 必须签署的主体 | 后续业务条件 |
| --- | --- | --- |
| 三方订阅主合同及费用附件 | 客户、实际出租方、宁达 | 全部签署及归档后开放押金和首期支付；资金到位及线上交接完成后才起租 |
| 交付延期协议 | 原订单三方 | 已确认报价、费用处理和现有延期条件齐备后更新对应安排 |
| 同价／升级换车协议 | 客户、同一出租方、宁达 | 已确认差价及服务费、资金处理、旧车归还和新车交付完成后生效；保持首版同出租方限制 |
| 原车续订补充协议 | 原订单三方 | 按新选商品冻结新增阶段；归档和资金条件齐备后待生效，到期按上海时间及现有激活规则办理，不提前改原阶段 |
| 交付前取消／提前终止及需确认的最终结算协议 | 原合同三方 | 协议、真实交还事实及财务条件各自成立后结束业务，不以签署代替退车或退款 |
| 未开始续期取消协议 | 原订单三方 | 保留期前取消约定及时间证据；新增续期实收全额退款，无取消费；退款／归档跨起租日不恢复该续期 |
| 合作协议及其条款变更／终止文件 | 合作商、宁达 | 双方确认签署并归档，按约定日期生效；保留版本及车辆、比例、期间快照 |
| 用印授权文件 | 作出授权的企业本人，按经核实的渠道流程 | 单独记录业务授权及渠道权限，不能混作普通合作协议的自动签凭证 |

不新增普通任意改价、跨出租方换车或其他已暂缓业务。原本未形成合同关系的申请撤回仍按申请流程处理；不能为尚无有效主合同的草稿生成虚构终止协议。

本方案的统一签署顺序为：业务审批及文件冻结 → 客户确认并本人签署 → 实际出租方签署 → 宁达签署 → 全部核验 → 法大大归档 → 宁达文件归档。合作协议省去客户步骤，并先取得合作商对具体版本的确认。这是实施选择，用于减少部分签署和重复派发，不改变合同里的实质条款。

### 6.2 文本与附件

- 依据现有已确认的交易规则编制电子签正式文本，不直接把“纸质签署、签字件上传、人工审核归档”的条款用于新文件。
- 新文本、用印授权及电子签相关隐私告知完成正文和打印／签署版样张后，交用户一次审定对应正式版本。系统不得发布未经批准的法律文本。
- 每份文件冻结模板版本、全文摘要、当事人、车辆、方案／报价版本、费用安排、合作协议和授权引用。附件明确属于同一签署范围，签后不可替换。
- 自然人和企业分别使用相应身份字段，不以企业信用代码填写自然人身份证栏。
- 各种姓名、订单号及中文文件名使用正确编码，统一生成可读的文件下载名；内容哈希校验不依赖文件名。
- 文本中不以接口账号所属公司代表平台，不出现晓浪业务参与、通知、备案或归档角色。

### 6.3 三个独立状态

“各方已签署”“法大大及宁达归档完成”“对应业务已生效”分别记录。订单、合作协议、续期、换车、终止各自依据权威事实推进，不把回调到达、页面返回、后台点击或人工备注记为签署完成。

未开始续期取消继续使用原有的期前双方约定证据阻止激活；电子协议签署可以后续完成，不能因签署或退款晚到而抹除已经确认的期前取消约定。

## 7. 数据和可靠执行设计

### 7.1 统一电子文件任务

扩展／整合当前签署模型为统一任务及逐方记录，承载订单和合作协议，不让同一合同同时落入两套可执行签章流程。可保留现有 `Contract` 与各业务模型的关联，底层表名由实施计划确定。

每份文件至少具有：业务类型和资源 ID、业务版本及哈希、批准模板版本、源 PDF 文件和哈希、供应商合同号、全部所需签署方、签署顺序和模式、各方独立交易号、冻结身份／证书／印章／授权、派发意图、可信查询证据、法大大归档结果、最终 PDF 和哈希、修订号、错误及审计记录。

订单协议须匹配三方，合作协议须匹配双方；不得通过“至少两人已签”或一个笼统完成字段放行。相同主体可能在多份文件中出现，但不能把一个文件的证据移用到另一个文件。

文档流程示意：

```text
准备并审批 → 冻结文档 → 等待本人签署／已授权自动签
                         ↓
                   分别核验每一方
                         ↓
              法大大合同归档 → 宁达最终PDF归档
                                      ↓
                      各业务分别检查生效条件
```

### 7.2 可靠性和回调

- 唯一业务键、文件版本、幂等键及数据库事务约束防止重复生成、重复签章、重复账单和重复生效。
- 外呼前持久化操作意图；使用任务锁／租约和修订号。请求超时进入待核验，先查询原交易，不换号重新用印。
- 每方签署回调验签并核对任务归属，然后通过受绑定的供应商查询确认；允许的无回显查询响应沿用现有 `fadada-query-response.md` 规则。
- 回调重放、乱序、错方、错合同、错交易、晚到回调和撤回竞态均不能使其他任务生效。前端返回只能提示查询。
- 所有必需方签署可信核验后才调用 `contractFiling.api`。官方资料说明归档后不得继续签署，所以不能在只完成客户或其中一家企业时归档。
- 用印请求始终绑定实际当事人的实名账户与印章，不以 API 的“接入平台”角色参数借用晓浪默认账户、印章或无需授权的执行路径。
- 归档接口以文档定义的响应结果为准，不把 HTTP 200 或缺省本地状态当成功；官方成功返回未必有备案编号，不伪造也不把可选编号设为必填。
- 法大大归档后下载最终 PDF，校验 PDF 类型、完整性、任务绑定及文件哈希，存入宁达受保护存储；下载失败保留“已签，归档处理中”，只重试归档／下载，不重签。
- 整份最终文档的合同验签结果、签署者身份与签署数量按当前 API 能力核实；任何证据不足都不标作完成。备份及取证文件同样受访问控制。
- 用户可见的签约链接短时有效且按本人、企业、任务、当前状态授权读取；不写日志、通知正文或公共文件地址，不跨企业泄露合同。

### 7.3 宁达自行通知与归档

业务事件进入本系统的可靠通知队列，按事务提交结果发送宁达待办、状态更新及结果通知，重试需幂等。供应商仅按已核实的本人认证／签署机制处理必要验证，不代替宁达业务流程。

合同准备、通知、签署请求、可信结果、法大大归档请求和宁达最终文件形成一条可审计链。所有 callback/return URL、存储、访问权限及档案管理使用宁达项目，禁止转交晓浪后台人工办理。

| 入口 | 用户可见结果 |
| --- | --- |
| PC 后台 | 合同中心统一显示实名准备、各方签署、归档及业务生效；支持准备／审批文件、发起、查看结果、按权限撤回或重发本人签署入口。去掉打印待签件、上传纸质签字件、纸质审核归档以及相关阻塞条件 |
| 客户小程序 | 保持“明朗原生”视觉及四入口；资料页可办理本人实名，订单展示三方签署进度、待本人签署动作和最终合同。协议完成后只有结果与查看入口，不残留过程勾选框 |
| 合作商 H5 | 增加本人企业／个人实名、有权人员绑定、印章、授权、合作协议确认和待签合同。自动范围内展示签署记录；手动模式提供逐份全文确认和法大大签署。只读公司管理员与签署人权限分开 |
| 现场员工端 | 保留现有验车与证据发布，使用实名员工账号留痕，明确客户实名确认和实际交付／归还状态；取消所有纸质或电子签交接单办理依赖 |

订单顶部进度、合同标签、首期资金、交接及客户订单状态读取同一套事实和操作能力：满足前序条件显示已完成，未到当前阶段显示未开始，只有确实缺少条件才显示阻塞，并给出具体原因。不能再出现已付款但首期资金仍阻塞、已交付却待交接签字等冲突。

签署按钮、手动回退及重试按钮根据服务端 `can...` 与原因展示；前端隐藏不代替服务端拒绝旧路径。旧纸档写接口关闭并返回可理解的替代入口；更新小程序版本后才能使用新写流程，旧体验版不得继续提交纸档操作。

合作协议失效或待重签期间，保留商品和产品配置，但相应车辆不能据失效合作关系发起新合同。现有商品的申请可用性按合作协议有效范围计算；前台提示暂不可申请，后台给出重签原因，不自动批量删除或重建商品。

## 9. 线上交接

四类 `DELIVERY`、`RETURN`、`SWAP_RETURN`、`SWAP_DELIVERY` 使用一致流程：员工发布当前证据版本 → 法大大实名客户本人阅读并确认 → 后台确认真实交付／归还 → 固定保存该次线上记录。

客户确认绑定本人会话、法大大身份版本、订单、车辆、交接任务、证据版本及已批准的线上交接约定。员工身份来自当前有效实名员工账号，不让客户端自由填操作人。

证据变更产生新版本，旧确认不能覆盖新证据；有异议时不允许后台跳过本人确认。完成后的记录只读，保持本次身份及证据，不因以后证书过期而重写历史事实。照片、文件、时间、确认、实际完成和访问日志按权限保存。

实名状态失效或身份不一致时，阻止新的客户确认并引导处理；运营不能勾选“已实名”代替法大大。交接记录不调用签署／盖章／合同归档接口。

## 10. 已授权测试资料清理

### 10.1 清理与保留清单

本轮授权清理的是测试业务，不是整个数据库。先制作按 ID 列明的只读清理清单、受影响关系和文件哈希，明确来源及保留原因，再在切换时执行。预演发现非测试记录或未确认的真实业务立即排除并单独说明，不扩大授权范围。

- 清理测试申请、订单、交接、纸质签署／审核档案、旧测试业务待办及相关占用／派发任务；根据真实资产资料解除由这些测试业务造成的预占／在租派生状态。
- 原纸质合作协议作废，其配置的比例、车辆及期间保留为待电子签的新版本草稿；不带入纸档为电子签证据，不自动激活新协议。
- 保留车辆、车型、登记人／所有人、BaaS、保险、合作商、关联车辆、产品、多产品商品配置和后台员工账号。
- 保留客户账号与资料及有效身份基础，不把业务重置做成客户身份冒用；重新发起的测试由客户本人重新确认。
- 保留真实支付、退款、押金台账、对账、供应商交易号、收退款幂等证据，以及保证这些记录可追溯所必需的账单和来源引用。

### 10.2 财务引用与文件边界

当前 `Payment → Bill → Order → Application` 及部分退款到服务阶段存在强关系。实施采用“财务记录保留必要来源、退出活跃业务列表”的方式，不为实现表面清空而强制断开外键或删真实账单。残存来源属于只读历史资金凭证，不保留纸质办理页面、签约流程或可继续履约的测试订单。

只读来源须标记为本次重置的历史测试来源，所有续费、催收、签章、交付和状态调度均排除它；支付／退款回调仍按原交易处理且可审计。没有财务依赖的测试记录可按清单删除。

清理前核对尚未终结的外部操作；已派发或结果未知的签署任务保留必要的交易绑定与回调处置记录，停用本地后续派发。晚到签署回调只核实历史事实，不重新创建已重置订单或激活合作协议；不为清理方便遗失外部操作关联。

纸质测试文件仅删除已列入清单且无其他有效用途的对象；通用上传、身份证、驾照、保险及车辆资料不得按目录批量清除。供应商已经保存的历史电子文档／授权不等于本地纸质测试文件，不擅自撤销、重签或声称已从供应商删除。

清理前做限权维护备份和可回滚记录。这是短期运维恢复材料，不恢复纸质业务功能；备份保留策略沿用现有运维策略，不额外复制成公开档案。

重置不执行退款、扣款或签章，不重新计算实际资金余额，不抹除已发生的交易。对需退还的测试实收，继续由原财务流程独立办理。

## 11. 验证与上线切换

先本地实现和模拟渠道核验，再执行明确范围的真实验收；旧系统和旧数据库不参与开发测试。

1. 身份／权限：本人、跨客户、跨企业、公司管理员冒充签署人、企业及自然人账户、失效证书／印章／授权、角色变更与管理员自审边界。
2. 文件：三方及双方所需签署人完整性、冻结全文及费用附件、签章位置、中文文件名、模板未批准、旧纸档接口不得推进。
3. 渠道：回调验签、重放／错配／乱序、无回显绑定查询、请求未知、自动转手动时不重复签、归档不可早于最后签署方、归档或下载中断恢复。
4. 业务：新订阅到起租；延期、同价及升级换车、续期、交付前取消、提前终止、最终结算和未开始续期取消；只有对应资金及实际交接满足时才生效。
5. 交接：四类均无签章调用；客户实名与证据版本绑定；异议修订需重新确认；完成页只读。
6. 清理：预演、保留清单、财务引用和迟到回调、测试占用释放、合作协议待重签、重复执行幂等与失败恢复。
7. 四入口：真实页面流程、所有状态一致、按钮及权限反馈、手机域名／回跳、旧体验版提示更新；不回退 Mock。

发布顺序：正式文本批准 → 渠道主体与手动／自动签模式核实 → 备份和迁移预演 → 独立代码审阅及回归 → 受控切换 API、后台、H5、员工端和小程序版本 → 已授权测试重置及合作协议重新签署 → 完整真实验收 → 发布所需验收结果。

涉及真实用印、合同签署、认证或支付的测试，在人物、企业、车辆、文件、金额和操作范围清楚后由本人／有权人员完成；不借“联调”自动签真实企业章。微信生产审核／发布与体验版设置分别记录，不能将上传包称为已发布。

发生故障先停止新派发、保留已产生的真实签署和资金事实，再恢复电子签服务；不回滚成纸质办理或用旧测试数据覆盖新事实。

## 12. 审阅时特别关注的实施选择

以下是本方案基于现有系统提出的选择，未冒充用户先前逐项确认：

1. 客户可先提交申请，但在正式电子签和线上交接确认前必须完成法大大实名；运营驾驶资格审核保留。
2. 统一采用客户 → 出租方 → 宁达的签署顺序；合作协议由合作商先确认再签署，宁达随后签署。
3. 保留真实资金必需的历史来源引用，从活跃订单／交接列表及调度中隔离；并非保留纸质工作流。
4. 自动签的供应商权限／主体未核实前按已确认的企业手签回退实施，不把未核实能力当作已开通；若手签也不满足主体要求，不发布该路径。

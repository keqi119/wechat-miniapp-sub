# 宁达 V3.1 合同自动填制与法大大电子签实施方案

日期：2026-11-07。状态：用户已批准方案并要求开始实施；未启用新合同、未发起真实签章。合作结算默认时限已由用户在本轮明确确认，个别例外另约。新增订单合同工作区与列表要求纳入同日实施计划任务10。

## 1. 结论与审阅边界

V3.1 可以在现有系统上实现完整自动填制，但当前版本尚不能直接按这组文书自动生成、签署并履行全部合同。身份、车辆、产品、订单、收退款、交接记录有大量现成来源；主要缺口是统一取值和冻结、少量主数据维护、计费与业务规则调整，以及现有电子签模块与实际页面和业务入口的接通。

“有数据库字段”“有 API”“当前页面可操作”“签署文本已正确带入”“真实渠道验收通过”是五种不同结论。本次以当前工作区源代码及实际路由为准，不把旧组件存在、历史测试截图或文书中的“自动带入”视为已经实现，也未连接生产数据库核实每家企业资料是否完整。

来源是用户提供的 `宁达订阅协议包_平台方强化版_20261106_V3.1.zip` 中 00—06 共七份文书。六份合同共 47 处方括号标记：24 处自动带入、4 处待填写、19 处电子签署控制区；一个带入块可以包含多个业务字段，不能把这些数量当作数据库字段数。00 的两处“待填写”是说明文字。已检查正文、表格、页眉页脚及修订标记，并将原文只读渲染为 42 页核对。原件不修改。

依据优先级：本次 V3.1 重澄清内容 → 本轮用户答复 → 此前已确认的业务边界 → 当前实现。与 V2.1 审阅结论不同的地方重新判断，不照搬旧缺口。

## 3. 采用的实现路径

沿用 2026-11-02 已确认的“现有法大大 API 适配层＋统一电子文书编排”架构，给它补上 V3.1 的数据、规则和页面闭环。

审阅过的替代路径：仅替换 PDF/Word 模板改动小，但不能处理实际交付起租、跨阶段日期、独立授权及退款规则；重新更换整套签约系统会新增迁移与主体隔离问题。本方案继续复用现有仓库，并把外部账号配置问题作为明确的渠道验收项。

按四个相互依赖的交付包推进：A 主数据与服务日历；B 合同生成与电子签证据；C 合作授权及订单变更/资金闭环；D 四端入口及受控验收。工程任务和接口另见同日实施计划。

## 5. 字段与页面的最小增量

### 5.1 企业资料一次维护

合作商和宁达分别维护经核验的企业全称、信用代码、住所、现行有权签署身份与权限来源、常设服务联系人和电话/可留痕渠道。邮箱只在实际提供并选择时显示。企业角色必须与法大大认证企业、实际签署人和印章匹配，后台管理员不因此获得企业签署资格。

合作商补齐经核验的对公收款账户及变更核验凭证；账户不从电池出租方收款账户推定。合作期间、每辆车适用期间、分润比例/生效日、产品版本与条件范围、主合同模板版本及固定内容进入合作条件快照。

PC 合作商详情增加“合作条件”“电子签与授权”页签；H5 挂载当前有权人员的实名、查看完整协议、逐份签署、独立授权及撤销入口。普通只读合作商账号不开放签署按钮。宁达有权人员使用独立企业身份入口，不能由普通 admin 会话代签。

### 5.2 产品与报价

新增 `minimumTermMonths`，与现有实际 `months` 分开。首轮建议保持现有“选择已发布产品卡”的交互：每个产品版本有明确实际月数和最短月数，满足 `actualMonths >= minimumTermMonths >= 3`；不顺带增加任意自选月数、任意议价功能。

02 附件一第四项只有一个最短期限“待填写”位置，但一份合作可能允许多个最短期限不同的产品。正式填制必须按产品版本逐行列出最短月数，不能统一填3或取某个产品值冒充全部。建议将该处审阅性单值句改为引用同一签署附件内的固定逐产品明细，同时保留均不得低于3个月的限制；这是需要在正式模板样张中确认的小幅表达调整。单一产品或所有产品同值时可直接带入共同数值。

新增面向客户的 BaaS 费用安排快照：已含月费/另付/无需该费用，另付时必须明确金额、周期和收款对象。车辆 BaaS 资产月租只表示资产成本，不能直接等同于客户应付。费用组成保留基础费、里程费及实际附加产品，合计与客户确认报价一致，金额整数分。

客户和企业资料、产品条件、车辆披露、保单事实、已确认报价均以版本引用和摘要哈希冻结。确有例外时维护例外内容、证据和确认者；常规订单不增加重复空栏。缺失未知与“明确无”严格区分。若人工最终报价与产品标准价格不同，应一次确认相应价费组成，使分项和总额一致；不能在合同中同时打印标准分项和另一个议价总额。目标车型另购换车附加品与当前产品单次费出现不同来源时，先核对客户已确认的有效约定，不能随意挑较高值或重复收费。

### 5.3 车辆、保险及资格

复用台账中的登记所有人、采购人、合作商关系、电池和权属资料；登记所有人不必等于实际出租方，需要出租权限证据。重要权利限制和车况从真实档案带入，不能用缺省空字符串表示“无”。

已出单时列示真实险种、保险公司、保单号；未出单时只有确已确认的投保安排可进入签前摘要，交付前必须补齐有效实际保单并核验。保单登记状态不推定保险公司承保、全部事故可赔或“出租经营专用险”。不复活已取消的保障要求模块。

身份证、驾驶资格沿用已有资格档案及有效性校验；法大大实名是签约与客户交接确认的另一个条件，两者不能互相替代。客户可先申请，签约和交接前必须补齐。

### 5.4 合同与履约事实分开

签前固定：当事人、模板、价格及计算公式、产品条件、计划安排、签前已知收退款/费用和明确例外。

发生后追加：渠道真实签署时间、实际交付/收车、里程读数、款项成功/失败、通知到达、真实取消合意及核验、归档结果。上述事件独立留存，不回写替换已签 PDF，不因后续交接改变签前快照哈希而强制重签。

## 6. 服务日历、费用与退款

### 6.1 统一日历

建立共用服务日历，订单永久保留首次实际起租日号。初期、续期、换车差价、账单和里程期使用同一版本规则。日期都按上海时区；区间 `[start, end)`，月底不足日暂取月末，下月恢复原日号。

初次签署只承诺实际交付起算规则和确认的计划安排。押金与首期可在交付前支付；第一次实际交付事务锁定 `actualDeliveredAt`、服务日历和首期账单期间，并把此前首期实收归入该期，不重开首期款。后续期应付日等于服务期起日。原先约定起租日和独立首期付款日的校验、报价文案需同步退出，已有真实支付流水保持可追溯。

`plannedDeliveryAt` 不能复用为 `actualDeliveredAt`。续期不能从 4 月 30 日重新取 30 作为原始锚点。提前结束/迟还涉及日内不足一天时，按已确认合同的实际时长比例算末期，首尾不重复；换车补差仍按 03 约定的自然日和服务月规则。

### 6.1.1 期前取消证据晚到的纠正

现行取消来源校验只接受未激活阶段，并把存在 `usagePeriod` 视为已真实履行；激活任务却会自动创建空期间。这两项必须一起改。系统 `ACTIVE`、自动账单、空期间、自动发放赠送次数均不能单独证明新服务真实发生。

有效双方期前合意晚提交时，先建立独立核验案并保留原操作时间，不受上述技术状态阻止。待核时暂停该争议续期的新增账单发布/收款及自动新权益发放，不停止原合同必要服务。核实真实合意确在新期开始前成立后，以取消事实作为新阶段未生效的依据，记录纠正版本和操作者：停止后续计费，撤销未付账单的应收效力但留原记录；全部新期真实实收走原路全退；空期间和未消费新增赠送额度作废留痕，已预占未交付的权益释放，不清除原期或另购权益。

若已有真实里程、交接、用车或权益消费，保留原始事实和资金，转入依赖事项核验；不得删除事实、直接把它变成续期已有效履行，也不得擅自从本应全退的新增款抵扣。继续占用、真实新增服务等是否另有约定或责任，按其独立有效依据另核。此纠正与定时激活、晚到支付/退款回调使用同一阶段锁和幂等事实编号，不能重新启期或二次退款。

### 6.2 换车与终止计算

同商换车的原押金完全沿用。已签新旧价格及公式不变，实际新车交付日变化只生成事实结算及补退，客户核对实际结果；如价格、车辆/产品方案等合同条件改变，另走有效变更。旧车收回至可用新车/已同意替代车交付间隔，按有效事实单列减租，不被已签差价或首期实收覆盖。

个人原因协商提前终止补偿为 `min(当期含税月费, 原合同未履行期间剩余租金)`，逐期按适用价格及服务月算剩余租金；独立车损、里程等有据另列。经营方违约、法定解除、交付前取消、未开始续期取消不套用这项补偿，也不加未提前 15 日通知罚款。

06 普通情况分开记录法律生效、实际收车、终止/停租依据；原合同未履行部分在有权人员实际收车时终止，最迟不超过原期止日。更早已有合意/停租仅以真实例外及证据录入。真实收车不能被未点击、未结清或归档延迟阻止记录。依法或有效约定的单方解除保留核验依据和通知证据路径，不强迫套用三方协商终止签署。

### 6.3 退款与押金

建立统一退款义务记录，而不是给每单手填退款承诺日期：场景、义务主体、对应债务/款项、无争议金额、触发事实时间、规则版本、工作日历版本、最迟发起日、渠道受理及最终结果。工作日历需支持节假日和调休，不能只排除周末；起算事实和确认过程保留证据，内部审批不重置时钟。工程建议从触发次日计工作日、到截止日23:59:59上海时间；此为本方案提出的实施口径，并非已经从现代码或模板识别到的独立字段。工作日历缺失年份时提示维护，不能自行猜节假日。

交付前取消和新期取消：取消已生效且无争议退款金额确认后 3 工作日。普通还车/06：实际还车且无争议结算确认后 7 工作日。03 明确的差价/无车间隔退款按该次事实及金额确认起算，不等整单最终退车。具体工作日算法和节假日数据上线前以已确认规则和日历固定。

发起、渠道受理、失败、到账分开。原路不可用时才进入客户本人替代账户核验和财务双人复核；不把合作商对公账户用于客户退款。已发生但未决的事项才建立保留金案件：金额上限、证据、待定责任、核查岗位/责任人、最迟释放日及扣抵同一债务的关联。无争议余额先退，不以原期争议抵扣已约定全退的新期款。

退款与资金调整继续双人复核。普通业务资料管理员可自审的既定规则保留；对客户退款的合同授权免合作商逐笔再批准，不免宁达财务权限和审计。

## 7. 合同生成与电子签

### 7.1 模板和不可变文书

分别登记 01、02、03、04、05、06，不继续用一个通用补充协议/终止正文混用。02 拆成“合作正文＋附件一二”和“附件三独立用印授权”两个独立签署任务，后者固定引用前者的合作条件与授权范围；独立任务不能因合作主协议签章而自动完成。拆分为签署文件是技术排版安排，正文和范围不得擅改，启用前核对两份完整样张。

正文、附件、摘要、编号、各方角色、醒目提示和签署区形成完整 PDF。保留 V3.1 的重要条款强调与附件顺序，不用纯字符串替换导致表格、提示或附件漏失。模板登记记录来源 ZIP/条目哈希、批准版本和确认人。未核定的文书不得发布为可签模板。

每个带入块映射明确字段来源、必需/可选/事件后置规则；不能留下“自动带入”“待填写”“以系统为准”的待填文本。电子签署控制区转换为三方各自定位；02 两个任务各自双签。用 `CUSTOMER/OWNER/PLATFORM` 业务角色映射各份甲乙丙，避免 02 甲方是宁达而其他文书甲方是客户的错章。

签前预览完整正文及关键条款提示，确认对应 `sourceSha256`；条件变化生成新版本。签后保存原 PDF、最终 PDF、模板/业务/源文件哈希、真实签署身份与权限、渠道交易和查询证据、验签及归档回执；后续履约事件只关联文书，不重写文件。

### 7.2 真实签署时间与归档

当前 `service.ts` 用 `verifiedAt` 显示 `signedAt`，`archive.ts` 同样用核验时间计算签署日，必须修正。当地保存的法大大 API 2.0 官方资料 4.6.4 明确有 `data.endTime` 签署时间；4.6.5 `contract_verify.api` 提供签章时间、签名信息及完整性/时间戳验证结果。接入时保留可信请求与合同/账号/交易绑定，分别存 `providerSignedAt`、`verifiedAt`、`archivedAt`，不能接受前端自报日期或用当前时间补缺。

各方有效签署完成与业务归档就绪分开显示。完整归档前可继续限制放款/交付等操作就绪，但不显示“合同未生效”否认已核实签署，也不得因归档慢延长租期或取消退款起算。验签检查完整文件、预期主体、印章和时间证据，不以“PDF 与源哈希不同”代替验签；一个主体有多个章时按证据映射，不粗暴要求签章数量恰等于人数。

### 7.3 企业自动签的双重条件

先核验渠道自动签权限，再核验宁达业务范围授权，缺一不可：

1. 客户个人和两家企业分别完成法大大实名；企业签署人员与权限证据匹配。
2. 02 主合作协议由双方有权人员逐份签署。
3. 合作商独立签署附件三，宁达独立确认；宁达自身用印也有真实有效授权。
4. 只有主订阅 `SUBSCRIPTION` 在合作、车辆、产品版本、月费/区间、押金、期限、权益、固定正文版本均在范围内，且当前渠道权限/印章有效时才能自动盖章。
5. 客户始终逐份本人签；主订阅顺序沿用客户→合作商→宁达。任一企业自动签条件不足，任务在派发前确定双方企业均手动。
6. 已有一方发起或部分签署时失去授权：先停后续自动动作，核验已接受交易；有效已签保留，未签企业本人补签，不重复盖章或以本地状态消除已发生签署。必要新版本须先安全关闭旧流。
7. 授权撤销/缩小范围收到后即停止受影响的新自动签；疑义先暂停再核验。不可因渠道状态缓存或重试继续用印。范围扩大须新有效授权。

03—06、合作协议、合作变更终止、和解均默认企业逐份确认。若以后想恢复它们自动签，属于另一个明确授权及正文范围的决策，不能扩大附件三。

### 7.4 渠道撤回与不确定结果

现有 `withdraw` 只是本地置 `WITHDRAWN`，不能阻止已打开的外部链接或已接受的自动签。增加停止派发、渠道关闭核验、关闭完成/需要人工处理三种结果；无法证明旧流停止时，禁止以旧合同已无效为由发布相互冲突的新版本。

本地 API 2.0 资料的 `reject_by_contract_id.api` 是合同拒签，且有打开/签署记录前提，不可直接称为通用撤销接口。渠道支持范围、部分签署、未知结果及旧链接失效须受控验证。完全有效签署的合同只能按适当后续法律文书或已有有效权利处理，不能后台删除代替解除。

本地停止后才核实三方已完整有效签署时，采用独立的“签署证据保全”路径：按原任务/版本/主体核验，回收最终PDF、真实签署时刻及验签证据；如需渠道归档固定文件，记录真实结果。各方仍可取得经核验的完整签后文件。该路径不调用业务 `afterArchive`，不把旧版本设为当前批准版本，不自动激活合作、订单或续期，也不取消原停止派发状态；同时生成需处理的签约事实事件。核验失败文件仅隔离留证，不冒充有效已签合同。后续由有权人员按真实签署及现有业务处理冲突，不能仅靠本地停止否认已发生的法律事实。实施时同步修订当前API文档“撤回后不能归档”的笼统表述，区分证据保全与业务推进。

## 11. 需确认、需维护与需供应商验证的区别

**已确认的商业规则**：00 第五部分原标为拟定默认；用户于2026-11-07本轮明确回复“采用这组默认值，例外另约”。采用自然月结算、次月第5工作日前出账、收到后5工作日异议、次月第15工作日前付款；补足2工作日且不迟于客户退款期限、已分润退款返还3工作日、完整开票资料后10工作日。实现为一组有版本的默认规则，单份例外经双方签署，不需要每单手填，也不再就该组值重复求批。此确认不等于现有系统已实现或全部模板已启用。

**资料维护**：各合作真实起止日期、比例/适用车辆、产品范围、对公账户和企业签署权限，必须从真实资料维护；不能由工程师猜测或从样张复制。既有数据缺项是否已补齐留待授权的实际数据核对。

**正文补充**：合作变更/终止及确需的特殊和解/主体模板，由法务补充或确认具体文本后启用。

**供应商核验**：当前应用主体隔离、渠道授权函、人工签署、撤销/关闭、验签权限和通知路由。它们不等于用户再批准一遍已有业务方案，也不应通过假造本地状态绕过。

## 12. 交付与验收

1. 固定 V3.1 来源、字段映射和业务规则，完成缺项清单；旧模板不自动转为已批准。
2. 先用合成数据测试日期、整数分、身份、范围授权、三方角色、版本冲突、未知结果、退款和四种交接，再做完整样张核对。
3. 在自有隔离数据库验证完整流程；不得连接旧业务库，不向旧系统推送/部署。
4. 真实受控验收需明确客户、两家企业、车辆/产品、文件种类及金额，由有权人员亲自实名和签章。真实支付/退款逐笔保留追溯。
5. 按此前确认的新电子签切换方式，旧测试纸档、申请、订单和交接可按明确清单重置；保留车辆/产品/合作条件及真实资金必要关联。先形成可审阅 dry-run 清单，不能遍历删除全部业务记录。
6. 四端共同验证：初签→首期/押金→实际交付→换车→续期→期前取消→交付前取消→协商终止；同时验证拒签、撤权、晚回调、实际收车后争议等分支。
7. 全部结果、启用模板和渠道核验依据齐备后，另行办理正式发布。本次只交付审阅结论与方案。

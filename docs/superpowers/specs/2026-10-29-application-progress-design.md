# 申请审核进度与阻断指引

日期：2026-10-29。依据用户“明确进度、卡在哪里、按钮后的流转结果”的直接施工要求。

## 真实问题

用户指定申请在只读核验时为IN_REVIEW、第2版候选DRAFT，当前信用有效，客户资格记录0条，本单风控未审核。受理只写IN_REVIEW；生成OFFLINE候选仍处于IN_REVIEW；本单风险审核通过才进入AWAITING_CONFIRMATION。现UI平铺操作按钮，重复受理仍可见，阻断藏在长信用信息后，操作反馈只有通用提交成功。

## 方案

采用专用申请详情工作区，沿用黄黑极简、统一DetailFrame抽屉。既有接口足够，集中聚合当前信用、资格及本单风险状态，不增加新业务状态或改变审核规则。仅换状态标签无法表达并行依赖；强制单线向导会把可并行的工作错误串行化，因此使用阶段条＋准备清单＋下一步指引。

主线：受理 → 审核准备 → 本单风控 → 客户确认 → 正式订单。审核准备内，身份与驾驶资格审核和信用核验可并行；信用有效后可生成候选方案，不必等待资格先完成。资格有效、当前信用有效及匹配的候选齐备后才可通过本单风控。客户确认后才生成正式订单；后续合同、支付、交车进入正式订单办理。

详情首屏显示当前阶段、精确说明、已完成事项、当前所有阻断和下一步。每条阻断有可执行入口，定位“客户资料”“信用核验”“方案风控”，或打开既有操作表单。当前IN_REVIEW隐藏重复受理；待补件可重新受理。不会隐藏需补件/拒绝等异常处理入口。

## 数据与交互规则

- 资格以qualifications.current.status为准，不以历史items中APPROVED替代当前有效性。
- 信用以服务端verificationCurrent、consentRequirementsMet和status判断；候选核对申请版本、信用版本、核验ID、规则与档位。canFinalize直接尊重接口。
- 风险RECHECK_REQUIRED表示须重新审核，不能以旧APPROVED继续显示可确认。无候选时不请求会返回前置冲突的risk接口。
- 加载、失败、无权限、未知状态必须明确标识；读取失败不当成“未提交”或“已通过”。请求取消/晚到响应不得串申请。
- 操作提交成功与最新进度刷新分别反馈；刷新失败明确“已提交，进度待刷新”，不误报审核通过。审核通过不宣称已发送客户通知。
- 真实订单存在时给正式订单入口；取消/拒绝有结束说明及原因，不能继续显示通用下一步。
- 资格资料提交/审核后同步刷新流程；保留详情分区和编辑输入。所有授权、独立审核、交易及合同校验保持现行服务端要求。

## 范围与验证

流程部分只改admin展示/操作引导。新增纯状态模型回归，覆盖并行路径、有效/过期信用、资格重新审核、方案不匹配、风险通过/失效、确认成单、取消拒绝、加载错误。浏览器用合成数据检验用户同款阻断、CTA定位、按钮反馈、资格更新、错误重试和窄屏。上线后只读核验，不代用户执行审核、确认或交易。

## 追加：证件有效期

用户追加要求身份证、驾驶证有效期可为“长期”，固定有效期只选择日期。两份证件分别选择固定日期或长期；长期时隐藏日期输入并发送明确longTerm标记和空日期，不使用2099等虚构日期。固定期限按北京时间有效期当天全天有效；旧ISO时间入参继续兼容，按其北京时间日期理解，不回写已有时间值。

资格版本新增identityLongTerm、drivingLicenseLongTerm布尔字段（旧数据默认false），原两日期改为nullable。固定期限必须有真实合法日期，长期必须无日期；客户端清除隐藏旧值，服务端拒绝矛盾组合。提交、独立审核、风险复核的有效期检查统一复用同一函数；长期仅免截止日检查，身份资料、证据归属和审核要求保持。

只执行一个增量迁移：放宽两日期非空约束及新增两个默认false字段。保留全部旧列数据和既有资格记录，不迁移为长期、不改已审结论。

## 实施选择

沿用 React/Vite、NestJS/Prisma、现有原生小程序及 H5；按指定 subscription-Saas 提取布局和业务设计，适配本项目模型。远端 UI 参考固定为 db4b48c55890f11f52c4fc52c29242d7c0d150be。整体复制旧工程会丢失当前线下合同、四入口和宁达权限规则；只改菜单不能补齐商品、线下变更和资产模型，因此采用逐模块替换及兼容增量。

## 第一阶段：已明确的基础调整

1. 使用显式 CUSTOMER_IDENTITY_POLICY=MANUAL_REVIEW 暂停新实名办理；未配置保持 PROVIDER_REQUIRED，未知值拒绝启动，防止配置拼写错误放行。公开 identity-config 和客户 profile.readiness 返回 identityPolicy。MANUAL_REVIEW 资料完整即可提交，realNameVerified 保持 false，不调用或依赖实名供应商；客户资格与风控审核仍在后续流程校验。
2. 新人工资料快照使用 version=2、identityPolicy=MANUAL_REVIEW、identity=null；保留 v1 法大大快照解析与已成单冻结记录。切换后尚未确认且快照口径不同的申请要求退回补件重新审核，不静默换凭据。
3. 小程序显示“未进行线上实名认证，由运营审核资料”，隐藏新实名办理及主动供应商查询入口，阻止缓存/旧页面重启实名。资料、登录、协议、付款及补件保持正常。
4. 先将已有功能按新结构归并：客户、车辆（含合作商和保单）、产品、订单、合同、财务、系统及驾驶舱。没有后端能力的模块不会使用空壳假冒完成；商品及其余新增模块随后按契约实现。旧记录深链、角色权限、列表返回位置保留。
5. 修复救援/事故提交丢失指定 orderId 的跨端缺口，保留服务端本人订单校验。

## 后续业务决策与施工

产品/商品使用明确版本及订单快照；同车可配多个商品，但订单事务只允许一份有效占用。产品规则参考旧代码，既有宁达合同费率不自动改写。里程、补能、换车的可选计费和周期需要逐项确认真实经营规则。BAAS、残值、折旧优先沿用旧仓库明确模型，不能从字段名推定新财务规则。

变更中心需支持 OFFLINE 订单的方案审批、线下补充文件归档及显式生效，并按生效日处理新旧权益及账单；不能直接解除现有禁止变更的守卫。催收以实际欠款为依据，外发通知和收费规则须有依据。

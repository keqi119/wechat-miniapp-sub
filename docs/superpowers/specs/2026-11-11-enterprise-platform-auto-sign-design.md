## 1. 已确认的目标与边界

- 2026-11-11 实施中最新确认：由客户流程发起的订单相关合同，客户逐份本人电子签、合作商和宁达自动签；合作商与宁达的合作协议及其变更/终止，合作商逐份本人签、宁达自动签。
- 自动签受托方为上海晓浪网络科技有限公司，沿用其现有法大大 API 应用。用户已确认晓浪具备自动签权限。
- 沿用原企业合作商 H5 办理授权。当前系统接收签署结果、调用渠道归档，并继续在宁达小程序、H5 和 admin 保存、展示合同。无需另接晓浪业务系统。
- 企业不再填写订单、车辆、产品、金额上下限、单独授权起止日期，也不再逐单确认签章范围。有效授权覆盖本企业参与的、订阅平台已支持的各类电子合同。
- 这里的“任意交易条件”仅表示取消签章授权环节的这些限制。原合作协议的车辆、产品、交易条件约束，以及业务审批、客户方案确认继续有效。
- 不修改已上线交易合同正文，不增加服务商条款、信息披露页面或弹窗。不增加客户自动签、自动扣款、交接电子签或其他财务自动化。
- 已有企业实名、证书和选章记录继续复用；材料改变或真实失效按既有规则办理，不能因版本发布要求重认证。

## 3. 实现路径选择

采用用户已选定的“现有 H5 + 当前晓浪法大大应用 + 本项目执行与档案链路”。复用已验收的实名、印章、签署顺序、回调、验签和文件阅读能力，新增独立版本的企业平台授权策略。

其他路径：

- 晓浪另建通知、归档系统：用户已明确不采用，会增加接口和资料迁移。
- 保留宁达受托、按车辆产品授权：与本轮已确认目标不符，旧记录只按原范围保留。
- 只改受托人名称或直接放开旧 scope：不能证明新授权，也会篡改历史授权语义，不采用。

## 4. 授权文件与业务合同的区分

现有 02 合作主协议第 4.1 条、附件一与独立附件三包含明确范围限制。按本轮确认：

1. 不修改这些既有正文和历史文件，也不扩大原合作业务权限。
2. 新自动签使用由企业本人实际签署的法大大渠道授权函，受托方为晓浪。不能继续套用旧宁达独立授权的签署证据。
3. 首次真实办理时，核对渠道实际生成全文中的授权人、受托人、自动签事项、终止安排及其对平台各合同种类的覆盖；保全签后文件与原交易绑定。
4. 若渠道函只赋予技术调用能力，或实际文本不足以支持本轮签章范围，记录为“授权范围待核验”，不凭本地标签自动扩大。此时提交具体差异供用户决定，不擅改交易合同或添加新协议。
5. 新授权只改变签章执行依据；合作条款、价格确定权限、客户同意、合同形成和变更等仍由现有业务数据与审批核验。

本地官方 API 2.0 文档载明：`before_authsign.api` 生成授权委托书，真实签署后取得自动签权限；可按授权合同编号查看下载；证书过期后需重新授权。`get_auth_status.api` 查询当前授权并返回关联授权合同、流水。取消通知需在法大大侧配置，不能假定原签署回调会自动收到取消授权通知。

来源：`.runtime/ninda/contract-fields-v31-20261107/provider/3.7.2.1.txt`、`3.7.2.4.txt`、`3.7.3.txt`；官方文档入口：<https://topen.fadada.com/index.html#/portal/documentCenter/P77J0UANKL/JEXT0Z0FQLYLAUAZ>。

## 5. 新授权模型

新增 scope v3，明确表达 `PLATFORM_CONTRACT_SIGNING`，不改变 v1/v2 摘要算法或历史记录。模型至少固定：

- 宁达业务平台标识与授权企业标识。
- 晓浪作为受托方的可信主体标识、完整名称及渠道应用绑定；与宁达作为合同签署方的身份分开保存。
- 实际授权法定代表人/经办身份版本、企业渠道账号、所选印章及签署证书。
- 本人发起和签署的授权合同号、交易号、签后文件哈希、可信查询或回调证据。
- 授权语义版本、真实签署/生效时间、渠道实际到期时间（有则保存）、暂停/撤销时间。

不要求企业选择合同类型或填写范围；服务端使用平台已支持的合同枚举，同时保留企业当事人归属检查。未知新类型、没有已批准模板或缺少业务编排的类型，不能因“全量授权”自动变成可办理。

页面不填写授权期间。系统依据渠道授权原文和真实有效状态判断，不用 2099 年等虚构日期表示永久有效。证书过期、授权撤销/失效或主体材料改变时暂停；仅证书核验时间变旧时先查询，不重复发起实名。

旧授权不自动迁移、不扩权。新授权办理不能回写已有任务的签署模式或合同快照。

## 6. H5 办理与状态

在现有企业详情、实名和合同列表风格内调整授权页，不新造入口：

1. 未授权：展示当前企业、已选印章、受托方及授权办理按钮；打开法大大原生授权页，由企业本人核对并签署。
2. 办理中：保存原授权交易，返回后查询该交易；关闭或重复返回不创建重复授权。
3. 授权成功：签署证据与渠道状态核验通过后启用本次授权，不再要求第二次点击“启用”或逐单确认范围。全局发布开关仍控制真实自动执行。
4. 已授权：显示状态、签署时间和授权文件查看入口；隐藏再次申请、时间输入和同意复选框。
5. 本地暂停：状态刷新不得自动恢复。恢复只针对原有效授权，不擅自生成新授权。
6. 撤销：沿用“点击撤销 → 填写原因 → 确认”的交互；先停本地新派发，再办理渠道撤销。未确认渠道撤销前显示处理中，不冒称已撤销。
7. 失败或未知：明确显示办理结果与可继续动作，不把未授权查询结果自动记为已撤销，也不把返回页面当作成功。

原独立用印授权记录继续按文件历史展示，新路径不再要求每单独立确认旧 V3.1 范围；历史授权与新的晓浪渠道授权保留各自来源、状态，不混用。

## 7. 全合同签署执行

### 可适用范围

主订阅、合作协议，以及平台已经具有已批准模板和可用业务流程的换车、续期、取消、终止等协议。其他既有枚举可复用相同执行策略，但不会为本轮补建缺失模板、业务流程或新增财务自动化。

首次授予、重新授予或扩大自动签权限的授权函必须由企业本人签，不能依靠尚未取得的权限自动签自己的授权。

### 每次派发的必要校验

- 本单业务已经通过原审批和客户确认；原合作业务范围、真实出租方、车辆归属仍匹配。
- 当前任务绑定的完整 PDF、已批准模板、交易快照和版本未变化。
- 客户保持手动签署；有客户的合同沿客户 → 合作商 → 宁达顺序。双方合作合同沿合作商 → 宁达顺序。
- 企业分别使用自己实名、证书和印章；晓浪是授权受托方，不替换合同当事人或印章所属人。
- 当前企业的新授权适用于本平台、该企业，未暂停/撤销，渠道查询新鲜且与原授权合同和流水匹配。
- 继续执行幂等、事务锁、重复回调校验、先查后重试及最终文件验签归档。

订单相关合同须双方企业均具备自动签条件；合作协议类仅宁达一方可自动签，合作商始终逐份本人签，不要求合作商取得自动签授权才能启动宁达自动签。所需自动签条件不足时保留已上线逐份电子签路径。已发起、结果未知或部分签署的任务，先查清原交易，不能直接重发或生成相互冲突的新合同。已签一方不重复盖章。

虚拟测试授权和原有 `MANUAL_ONLY` 任务不能被本次全局配置自动放开；新的自动签渠道验收另有明确范围。

## 8. 通知与档案

沿用当前应用和项目回调域名、鉴权及档案存储。技术调用与业务责任的角色描述按本轮已确认方案调整，合同当事人仍是客户、宁达及实际合作商。

核对当前应用的取消自动签异步通知配置；同时保留每次自动派发前的可信查询，以处理撤销回调未到达的情况。不同企业、其他项目、旧环境的回调和任务不得互相作用。

授权书及合同的签后文件、渠道核验、真实签署时间保留在本项目档案中。三端继续使用已验收的参与方打勾和“待签署 / 待归档 / 已归档”展示。

本轮不新增个人资料采集、客户端隐私接口或披露页面。既有主体资料与文件访问权限不因代理签章关系扩大。

## 9. 改动位置与验证

主要影响：

- API `owner-signing`：v3 范围、受托方、授权请求/刷新/撤销、签后授权文件、成功启用。
- API `electronic-documents`：受托方与合同平台分离，扩展企业自动签策略到已有合同类型，移除新策略对旧车辆/产品签章授权范围的依赖。
- 合作及其他合同的准备入口：保留原业务依据校验，处理合作协议没有订单上下文的自动签。
- H5 授权页及 admin 状态：复用既有页面结构，简化新授权操作，提供真实状态及定位。
- 小程序：客户签署方式不变；核对合同状态、签后阅读和后续业务联动即可。

先补关键测试再实现：主体/印章隔离、所有已支持合同种类、无订单合作协议、客户始终手签、旧范围不扩权、实际合作条件仍拦截越界交易、首次授权本人签、重复返回/授权回调幂等、暂停不被刷新恢复、外部撤销、证书变化、未知结果不重复签、双企业自动签与归档。

不将新策略引入旧业务库或旧系统；仅本项目改动。与其他工作区修改隔离，根锁文件由主控处理。

## 10. 发布顺序

1. 完成实现、本地测试与独立审阅；先部署兼容的新授权办理能力，自动执行保持关闭。
2. 在原 H5 由双方本人办理真实渠道授权；核对实际授权文件是否支持本轮方案，并保全证据。
3. 在明确确认的验收范围内验证企业自动签、撤销拦截及签后文件归档，不复用手签测试结果冒充自动签验收。
4. 验收后正式开启新策略；只有实际签署新授权的企业进入自动模式。

“已有代码”“用户确认渠道有权限”“企业实际授权”“真实自动签验收通过”分别记录，任何一项不相互替代。

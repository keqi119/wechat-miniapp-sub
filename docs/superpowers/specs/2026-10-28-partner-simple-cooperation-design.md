# 合作商简化登记与企业服务设计基线

日期：2026-10-28（Asia/Shanghai）  
版本：v2.3（已于2026-10-28上线，运营直接办理，不要求分权复核）  
替代范围：v2.2 中合作商登记、管理员开通及分润统计办理流程。客户支付、退款、车辆交还及逐单线下合同保持各自职责。

## 1. 用户已明确的要求

1. 平台后台为每家合作商设定公司管理员，采用电话号码与邀请码，从服务号“企业服务”登录并确认绑定。
2. 合作商详情上传合作协议、填写合作商分润比例、关联车辆；其他合作资料非必填。
3. 公司管理员只读查看合作项下车辆状态与分润，支持按协议、车型、时间期间等维度统计。
4. 分润基数为实际收到的租金减去已退租金；押金不计入。比例由运营填写，系统不得预设20%或80%。

本次收敛目标是“运营登记合作事实 → 公司管理员确认绑定 → 查看车辆与自动统计”。不要求运营另行编制规则、结算单或完成人工付款登记，才能看到统计。

## 2. 实现方式与取舍

采用用户提出的简化方式：在现有合作商详情内直接登记协议、比例和车辆；统计直接使用真实租金收退款事实。沿用后台、服务号 `/owner/` H5、短信通道与独立合作商会话，不增加应用或认证供应商。

只合并旧审核表单仍会保留原来的提交、核验和下单阻断，不符合“其他事项非必填”。另建一套独立分润系统会造成车辆和支付来源重复，因此不采用。这些差异在当前代码中确实存在，实施必须修改服务端业务条件，不能只删页面字段。

用户于2026-10-28确认“直接办理，不要求分权复核”。首登/后续登录方式、可选日期含义、比例冻结与统计归期按本设计实施。

## 3. 后台合作商详情

保持黄黑极简视觉，以及车辆详情一致的抽屉、顶部操作区和“处理概览／详细资料”结构。常规办理集中在概览，其他资料折叠显示。

### 3.1 公司管理员

- 每家合作商一个当前公司管理员；后台录入手机号，姓名选填。
- 运营点击“生成邀请码”，系统展示可复制的一次性邀请码和企业服务入口。运营自行交付对应人员，本次不自动发送邀请短信或其他消息。
- 状态仅展示“待绑定／已绑定／已停用”。可以重新生成邀请码、更换管理员、停用访问。
- 受邀人本人在企业服务确认后绑定生效；不再要求后台候选保存、提交及另一位运营复核三个步骤。
- 公司管理员是合作商只读身份，无需新增后台员工账号，无需注册客户小程序，也不自动成为法人或协议签署人。
- 同一个手机号可分别接受多家合作商的邀请，登录后切换已绑定公司；一个邀请码只覆盖一家。
- 管理员尚未设置或尚未绑定，不阻断合作登记、车辆发布及客户下单。

### 3.2 合作协议

一个合作商可以有多份协议，每份协议单独记录比例及关联车辆，满足按协议统计。

| 项目 | 必填规则 | 操作说明 |
| --- | --- | --- |
| 协议文件 | 保存有效协议时必填 | PDF或图片，可上传多页；上传即作为运营登记的合作依据 |
| 合作商分润比例 | 保存有效协议时必填 | 0%至100%，最多两位小数；空值与0%明确区分，无默认值 |
| 关联车辆 | 保存有效协议时至少一辆 | 从车辆管理已有档案中选择，可搜索车牌与车型 |
| 协议名称、编号 | 选填 | 名称未填时采用文件名；系统自动生成内部编号供区分 |
| 协议起止日期 | 选填 | 未填写表示系统不额外设日期限制，不伪造合同签署日期或续期承诺；填写后按所填范围约束新订单 |
| 联系人、地址、信用代码、签署人、授权材料、备注等 | 选填 | 不作为合作登记、协议保存或车辆绑定的前置条件 |

建立合作商档案仍需一个名称以识别主体；原企业／个人类型保留。登记合作协议不要求法定代表人认证、签署页逐项勾选、原件保管地址、分润扣除规则、结算周期、收款账户等旧必填项。

“保存合作协议”一次完成协议文件、比例与车辆登记，成功后用于新订单。无须再新建分润规则、提交合作批次或逐领域复核。资料不全时允许“保存草稿”；界面只指出上述三项缺失，不制造额外待办。

一辆车在同一时点只适用一份当前合作协议。关联已属于其他有效协议的车辆时，界面显示现有归属并要求明确替换，不自动抢占。变更保留历史，已成立订单不追溯转移。

替换协议文件、修改比例、调整适用车辆都产生记录版本。页面维持一个“编辑／保存”流程，系统在后台保留版本，无需运营手工创建版本对象或填写内部ID。

### 3.3 分润概览

详情内展示筛选条件、实收租金、已退租金、净实收租金、合作商分润、平台留存及明细。与服务号使用同一统计接口和计算口径。

不显示“应付账款、已付款”来代替自动统计结果。历史人工结算和实际付款仍留作历史记录，不作为本次统计前置，也不重复叠加到租金流水中。

## 4. 服务号“企业服务”

### 4.1 登录与绑定

首次流程：打开企业服务 → 输入手机号和邀请码 → 查看对应公司名称及只读范围 → 点击“确认绑定并进入”。

邀请码只授予后台指定手机号对指定公司的只读访问；输入手机号不等同在线实名或企业电子认证。系统按邀请码凭证核对指定手机号，不从手机号相同推导其他公司权限。

绑定成功后邀请码失效，建立独立合作商会话。后续会话有效时直接进入；退出、换设备或会话失效后，使用该手机号加短信验证码登录，不反复要求管理员发邀请码。已有绑定人员收到另一家邀请时，也可以通过“绑定其他公司”进入相同确认流程。

邀请码采用安全随机值、限时有效、限次尝试、一次性消费、服务端哈希保存。建议7天有效；重新生成后前一码立即失效；重复确认同一成功请求不产生第二次绑定。邀请码不进入URL、常规日志或审计明文。预览通过短时受限令牌关联同一邀请版本，确认时再次检查有效性。

更换管理员立即撤销旧手机号对该公司的访问，界面在保存前明确提示；新管理员确认前状态为待绑定。停用同样即时生效。只撤销这家公司的授权，不影响同手机号的其他公司。未撤销的现有有效绑定可以继续短信登录，不要求无意义地重新绑定。

“确认绑定”仅确认查看身份，不代表签署合作协议。H5业务资料仍只读；登录、邀请码预览/接受、验证码请求及退出为明确列出的认证操作，不能因此重新开放旧电子签、资料编辑或反馈写接口。

### 4.2 页面内容

| 页面 | 主要内容 |
| --- | --- |
| 概览 | 公司名称、当前管理员绑定状态、合作车辆数、本月分润摘要、合作协议入口、平台联系电话 |
| 车辆 | 车牌、车型、车辆状态、当前适用协议；支持车型与状态筛选，点入查看该车分润 |
| 分润 | 日期范围、协议、车型及车辆筛选；实收、退款、净实收、分润及明细；可按月、协议、车型、车辆分组 |

默认显示当月，提供本月、上月、本年与自定义期间。筛选可组合；金额卡片与明细使用同一条件。零笔收入显示真实的0与“本期暂无租金流水”，不能把尚未绑定、读取失败或来源不完整显示成0。

车辆状态直接映射车辆/订单的真实状态，不通过有无结算单推断。企业可以查阅本范围合作协议文件。默认不增加独立客户资料或客户订单列表；统计明细仅需要车牌、车型、协议、流水发生日期、租金/退款金额、适用比例及分润金额。客户姓名、手机号、证件、风控、银行账户及内部备注均不进入该统计接口。

## 5. 统一计算规则

### 5.1 纳入范围

仅纳入已确认成功且无需对账处置的 `SUBSCRIPTION` 租金收款及其已成功退款。押金、违约金、超里程费、其他补收、待支付和失败交易不计入。通过真实支付对账消除异常后，再按同一成功事实加入，不能重复入账。

对每笔租金来源，按订单当时冻结的合作商、协议版本、车辆、车型和合作商比例统计：

`合作商分润 = 净实收租金 × 该笔来源适用的合作商比例`

`平台留存 = 净实收租金 − 合作商分润`

多份协议或不同版本的比例不同时逐笔计算再汇总，不能对总净实收套用一个当前比例。比例由运营填写；历史“平台20%”不得被静默迁移为本次比例。

### 5.2 期间与退款

- 统计采用北京时间自然日；用户选择起止日期时包含首尾两天，接口内部转换为半开区间。
- 收款按首次确认成功的发生时间入账；退款按成功退款发生时间扣减。
- 跨期退款计入退款发生期，并沿原收款的合作商、协议版本、车型及比例冲减，不使用退款时的新协议。
- 退款期净额和分润可以为负数，不强行归零。
- 同一收款或退款只记一次；不得同时使用“已扣退款的收款净额”和独立退款负数，造成重复扣减。
- 修改车辆当前所属公司、车型名称或协议比例，不重写历史统计归属。历史车型沿冻结记录展示；现有车型ID可用于稳定筛选。

例：10月收租10,000元，当时合作商比例75%；11月退租金2,000元。10月分润7,500元，11月分润−1,500元，两月合计6,000元，即净实收8,000元的75%。该例仅解释算法，不作为真实合作比例。

### 5.3 金额精度

金额采用整数分，比例采用整数基点。正向分润四舍五入至分；分次退款采用原收款的累计净额计算差值，最终全额退款必须完整冲回原分润，不留下逐笔取整尾差。页面、分组、合计、后台和H5共用同一结果。

统计展示“按租金流水计算的分润”，不自动向合作商打款，不把该值标记成已支付。本次合作商办理不设置经办与复核分权；实际客户支付与退款仍校验操作者权限、真实渠道结果及金额，不能人工伪造到账。

## 6. 权限及订单连贯性

平台管理员与运营岗位维护简化合作资料和邀请码；公司管理员只读。由ADMIN和OPERATIONS岗位获得本次简化登记与邀请操作能力，后台用一项“合作商管理”能力表达，服务端按同一岗位范围校验；不将该简化能力扩展为退款、付款、收款账户或历史财务审批权限，也不要求运营逐项开通旧合作资料、规则、账户和结算等十余项能力才能登记一份协议。现有员工角色边界、离岗停用、会话撤销、操作审计仍须服务端执行；客服、现场员工不因此获得合作编辑权限。

本次移除合作登记、分润比例保存及邀请码开通的多级提交/复核步骤。用户最新要求覆盖此前合作商经办/复核分权约定：本模块直接办理，不再要求另一人员审批或核实人员映射。历史人工结算保留查阅，不纳入新版正常办理；本轮不扩展客户退款/风控/逐单纸质合同等其他模块的角色权限或改变支付渠道事实校验。

新订单的合作条件统一为：合作商未停用、本车关联有效登记协议、协议文件存在、合作商比例合法；可选日期已填写时满足对应期间。协议尚缺上述三项时可保存草稿，但不把草稿作为有效协议。管理员是否绑定不参与车辆可申请判断。

车辆及产品可售、客户风控、逐单线下合同、支付、保险和实际交接照常办理。尤其不能只放开车辆列表按钮，仍在申请、报价、确认订单或出租方告知中沿用旧主体核验批次、独立车辆审核、复杂规则或原件元数据前置。

可选主体资料为空时，新合作登记及申请不得拦截。逐单文书如需这些资料，留在本订单纸质合同办理阶段补充；不能回头把它们升级成合作商必填。不得伪造缺失内容、实名认证结果、协议审定或客户同意。已发布法律模板不自动改文案；实现应确保未填字段不会以模板占位符展示给客户。

现有订单的出租方资料告知及客户授权保持原样。新版统计只提供公司车辆与金额，不因只读身份新增客户个人资料共享权限。

## 7. 技术落点与接口草案

本节为已批准的实施目标，不代表这些接口已上线；接口实现与发布进度分别记录，不用文档状态替代线上验证。

### 数据复用与新增

- 复用 `VehicleOwner`、车辆档案、存储文件、后台员工、独立 `PartnerPortalAccess/Session` 和短信登录能力。
- 新增简化合作协议及不可变协议版本，记录协议文件、合作商比例、车辆范围、可选日期和操作者；复用已有车辆关系表表达当前登记关系，不伪造旧APPROVED/复核人员字段。
- 邀请绑定记录包括目标合作商、手机号检索值、邀请码哈希、有效期、使用/撤销状态与访问版本。沿用现有手机号加密与脱敏方案，不使用旧Customer邀请或法人电子签绑定。
- 新增分润统计事件，或在现有支付事件上建立等价的可追溯只读投影；至少唯一绑定成功收款/退款、金额、首次成功时间及订单合作快照。数据结构以实施审阅后的最小兼容方案为准。
- 新订单明确冻结协议版本、合作商比例和车辆/车型归属；旧快照使用原算法解释，不重算已确认的摘要。

### 后台

- 合作商列表、详情沿用现有入口；简化主体DTO的可选字段，保留名称和主体类型。
- `GET/POST /admin/partners/:ownerId/agreements`：列表、保存协议；编辑版本采用明确协议ID与revision，文件和车辆归属由服务器校验。
- `POST /admin/partners/:ownerId/agreements/:agreementId/stop`：停止用于新订单；保留历史统计。
- `GET /admin/partners/:ownerId/company-admin`：管理员及待绑定状态。
- `POST /admin/partners/:ownerId/company-admin/invitation`：设置手机号并生成/重发邀请码。
- `POST /admin/partners/:ownerId/company-admin/disable`：立即撤销该公司访问。
- `GET /admin/partners/:ownerId/revenue`：统一筛选与分组统计。

所有写操作保留revision、事务和幂等，不把版本冲突留给前端猜测；敏感邀请码仅生成响应展示；生成请求只产生一个有效邀请。若响应丢失，不泄露已有邀请码明文，返回可恢复的待邀请记录，由运营明确点击重发；重发原子撤销旧码并生成新码。

### 企业服务

- 新增邀请码预览与确认绑定认证接口；预览不返回车辆、金额或文件，只返回待确认公司名称和只读范围。确认成功后生成现有独立portal会话。
- 沿用短信登录、会话检查和退出；授权判断支持新“运营邀请＋本人确认”事实，不再强制旧 `reviewedBy/reviewedAt`。
- 新增已绑定公司范围内的协议查询、车辆筛选与分润统计；业务读取逐请求核验公司范围及访问版本。所有新增文件下载也走归属检查，禁止直接公开文件。
- 分润查询参数：`from/to`、可选`agreementId/modelId/vehicleId`、`groupBy=month|agreement|model|vehicle`，明细分页。筛选值仍需属于当前授权公司，不能用另一个公司的ID探测数据。

### 必须同步修改的当前文件范围

- 合作前置：`partners/{types,admission,cooperation,vehicle-binding,revenue-rules}.ts`、`vehicles/application-eligibility.ts`、`orders/business-gates.ts`、`owner-signing/lessor.ts`、`offline-documents/readiness.ts`及引用方。
- 登录范围：`partners/portal-access.ts`、`partners/portal-session.ts`、`owner-h5/{auth.controller,access,service}.ts`及独立邀请服务。
- 统计事实：支付成功/退款成功的事务入口及新统计服务；`settlement-sources.ts`的人工分摊结果不得直接用于此统计。
- 界面：后台 `partners.tsx`及导航/权限显示；H5 `owner/{Login,App,OfflineWorkspace,PartnerSettlements}.tsx`及查询模型。

当前Payment/Refund只有createdAt、updatedAt，不能把会随状态或对账变动的updatedAt当长期统计发生时间。实施需要首次成功时间或不可变事件来源；历史有据可查时迁移，不能猜日期。

## 8. 迁移及验收

保留已发布车辆、产品、合作商、协议原件、订单及资金事实；不重新清空数据库。旧规则和结算转为历史查询，不自动转成新统计金额。

既有比例不能默认填20%或80%。文件和已确认车辆关系可按可靠来源预填供运营核对；缺少协议或比例的记录显示待登记，不补造真实材料或审批结果。旧有效查看授权可以继续使用；未生效候选转为可编辑待邀请资料，不能自动开启访问。

按依赖实施：先确定协议版本/邀请/统计接口及兼容迁移；再完成后台简化和服务号绑定；同步替换新订单合作前置；最后接通净实收统计并整链验收后发布。服务号菜单拟使用“企业服务”，保留现有 `/owner/` 地址；发布时核实实际菜单，必要变更仅针对该菜单，不改员工工作台入口。发布前仅合成测试，不自动发送真实邀请或代替受邀人确认绑定。

验收至少包括：

1. 无客户账户、无公司管理员绑定，仅凭合作商名称、协议文件、比例、车辆即可登记并通过新订单合作前置；其他合作资料为空不触发隐藏旧门槛。
2. 手机号与邀请码不匹配、过期、重发后的旧码、跨公司码、并发重复消费均拒绝；本人确认成功可见唯一授权范围，其他业务写接口仍拒绝。
3. 换管理员或停用后，旧会话、旧短信挑战、旧邀请码不能恢复已撤销的公司范围；其他独立公司授权保持正确。
4. 订单锁定协议及比例；以后编辑协议、替换车辆归属或改号不改写历史订单和统计。
5. 成功租金/押金/其他费用、部分退款、多次退款、全额退款、跨月退款、不同协议比例、重复回调、待对账及解除对账逐项覆盖；无双扣退款和分币尾差。
6. 协议、车型、车辆、月份分组与筛选合计一致；后台与H5一致，UTC与北京时间跨日边界正确；退款期允许负数。
7. 不能跨公司查金额或协议文件，不泄露客户与内部资料；仅有统计数据不被标为实付成功。
8. 后台从合作详情能连续完成登记及邀请码生成，H5能首次绑定、退出后重新登录并查看筛选结果；桌面与手机均保持黄黑极简风格。

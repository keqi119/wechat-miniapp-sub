# 后台紧凑列表、整页详情与交付前取消流程

日期：2026-10-30。状态：设计方案与交互预览；本轮没有执行订单取消、退款、审核或发布生产页面。

## 1. 目标与依据

用户反馈：详情抽屉虽然已扩大到 1180px，但标题、状态、流程及分区常驻顶部，实际详情只能占半屏；一级列表也有重复标题、模块说明、子导航及工具栏，挤占数据区域。需要统一重排信息层级，保持宁达黄黑视觉、操作习惯和既有业务约束。

当前真实组件在 1440×900 下，订单 `.detail-panel-scroll` 高度约 484px。主要占位来自抽屉标题、状态区、流程图和标签栏；正文还重复呈现节点待办和分区标题。调整宽度不能解决此高度问题。

一级列表则主要是普通文档流中的占位叠加，并非这些区域均固定定位：70px 全局栏、36–44px 顶部留白、模块说明/导航、大标题/副标题、77px 搜索条；Manager 还将新增动作单独做成一张卡片，保单标题前有重复保障要求入口。订单多达 17 项、合同 10 项子导航换行会进一步增加高度。改造应合并层级，而非把所有旧区域改成固定栏。

## 2. 统一页面骨架

### 一级列表

```text
全局导航 │ 顶栏：模块路径                                  账户
         │ 模块标题 + 子视图/记录数                 主要新增操作
         │ 关键词 / 常用状态 / 筛选 / 刷新          高级筛选
         │ ┌ 表头 ─────────────────────────────────────┐
         │ │                                             │
         │ │              数据表格主体                   │
         │ │                                             │
         │ └ 分页与总数 ─────────────────────────────────┘
```

- 桌面统一预算：全局栏 56px、标题/子导航/主要操作合并行 44px、常用筛选 44px、上下间距合计 16px。模块名只出现一次，面包屑仅提供路径。
- 取消首屏大块说明、英文装饰眉题、重复页标题和无操作价值的页尾安全提示。必要说明放在标题旁“说明”入口内；错误和阻断仍在对应区域明确展示。
- 子视图与模块标题同排；订单常显“正式订单/申请与报价”，其余按资金账务、交还与用车等分组入口收纳，避免十余个标签换成多行。保单将档案/续保/保障要求放入同一导航行；单一合作商列表不重复渲染同名子标签。高级筛选默认折叠，展开后有清晰的已选条件和“清空”。常用关键词、状态、刷新和主要新增按钮直接可见。
- 表头在表格区域固定，表体滚动，分页固定于表格底部；表格是主滚动容器。避免同时出现页面、卡片和表格三层垂直滚动。
- 普通文本至少 14px、行高约 44–48px，按钮点击区域不少于 36px，移动端不少于 44px。以减少重复区域提升密度，不通过缩小正文获取空间。
- 横向溢出的宽表只在表格内部滚动；关键标识列及操作列在适合的宽度下固定。列宽以内容含义配置，长说明显示摘要并进入详情，不撑高每行。
- 列表条件写入白名单 URL（关键词、状态、页码等）；按当前用户和列表 URL 保存滚动位置。返回列表恢复条件、页码及位置。
- 1440×900：表格整体约 740px，扣除 36px 表头与 40px 分页后，表体约 664px；1366×768：表格整体约 608px，表体约 532px。以完整浏览器实际可用视口测量，默认未展开高级筛选、无错误提示时验收；错误信息和必要的筛选不为高度指标被隐藏。
- <=800px 收起全局侧栏，常用筛选允许两行；复杂条件用筛选面板，保留当前条件提示。表格或有明确字段的卡片按模块需要显示，不将全部字段压成小字。
- 搜索语义与接口一致：ResourcePage 现有服务端搜索继续沿用；Manager 目前部分列表只过滤已加载页，保留明确“筛选当前页”标签。不能仅统一外观就宣称搜索全部数据；跨页搜索需按具体接口补充查询和分页回归。

### 长详情

```text
全局瘦导航 │ 返回列表 / 订单号 / 状态 / 客户与车辆        刷新
           │ 本单导航            │ 当前分区标题 / 主操作
           │ 履约流程            │ 当前待办（简短，可展开）
           │ 客户与方案          │
           │ 合同与资金          │    本分区资料和办理表单
           │ 车辆交接            │    单一主体滚动区
           │ 用车/还车/结算       │
           │ 取消订单            │
```

- 订单、申请、合同档案、保单等长流程直接进入独立整页工作区。全局菜单在工作区可收为约 72px 的图标栏；保留名称提示与展开能力。本单导航约 192–216px。
- 独立详情替换列表内容，不叠加列表页的模块简介、子导航、标题和页脚，也不使用 Drawer 的 modal/focus-trap/body-lock 语义。
- 详情顶栏 64–72px，仅显示标识、业务状态、返回和少量操作。分区标题/主要操作一行，复杂当前待办随正文滚动；不再把完整流程图固定在内容上方。
- 主流程在左侧展示，可看到已完成、当前、未开始节点；资料分区与取消分支在同一本单导航中组织。导航内可折叠分组，不叠加多层侧栏。
- 右侧主体单一滚动区，卡片与表单自然流动。长条件清单默认显示具体首要阻断和数量，可展开；关键字段先展示，原始记录和历史版本按需展开。
- 1440×900 详情主体可视高度目标至少 720px；1366×768 至少 600px。不是截图里留一块空白达标，而要实际可见至少一组业务字段/一张表/一份材料与动作。
- <=800px 本单导航变为“分区”按钮与当前分区标题；弹出导航后选择内容即收起，不保留四层固定栏。
- 编辑、上传、登记退款等短动作保留抽屉。关闭只退出当前操作，回原分区和位置；Escape 不退出整个工作区。复杂多步操作在正文办理。
- 继续支持 `#orders?record=…&view=…` 深链接。进入记录增加历史项，分区变化替换当前 URL；浏览器后退、返回列表与返回关联来源均有确定行为。
- 按用户/订单/分区保留已访问区的输入与滚动；跨订单时隔离草稿和异步响应。敏感资料不写入 localStorage。

## 5. 单列取消流程

```text
纸质签署核实 → 独立复核 ──────────┐
已签：三方终止文件 → 原件归档复核 ├→ 最终核验 → 确认取消 → 结果
渠道支付核清 → 如有实收则退款成功 ┘
```

取消页包括“概览、签署核实、终止协议、资金核查、确认取消”。前三项准备条件按实际依赖显示并行关系，避免误导为必须从头逐项线性点击。

1. 核实签署情况，上传后台证据和说明。已有历史已签原件不能填“未签”。尚不确定签署情况时必须继续核实。
2. 独立复核取消依据；提交人、证据上传人不能审核同一版本。当前业务条款变更后需重新核实。
3. 已签的订单必须办理匹配当前商业条款的三方终止档案。取消页直接提供本单的“建立终止协议/继续归档”入口，不要求跳到全局合同中心重新选择订单。
4. 核验无在途支付、待批或处理中退款；所有实际已收款逐笔成功退清。退款审批不等于退款成功。订单没有实收时标为“无需退款”，不生成虚构退款单。
5. 服务端完整条件通过后，才开放“确认取消”；提交显示本次影响范围并要求填写真实原因。命令使用最新订单 revision 与幂等键，在事务内锁订单重查全部条件。

提交取消核实不会改变原订单状态，也不会冻结交付、支付或账单自动发布。页面同时显示“原订单：待支付”和“取消办理：待复核”，不发明已经生效的“取消中”订单状态；离开取消页不算撤回已提交核实。是否新增业务冻结须另行明确，本方案不隐式改变规则。

最终成功结果：订单 CANCELLED；未结束账单（DRAFT/REVIEWED/PENDING）作废；权益失效；未完成交接变为历史版本；车辆解除本单预留，转为 UNPUBLISHED，需要运营明确重新上架。合同、收退款、已归档证据和审核记录保留。确认取消不应宣称“车辆已自动上架”。

已完成正式交付时改为“提前还车与结算”分支：真实还车/查验/客户确认/纸质单归档 → 正式完成还车 → 费用、里程、押金、退款及必要终止资料 → 完成结算。不能走交付前取消。

## 6. 后端与权限要求

目前 `GET /admin/orders/:id/offline-cancellation` 只返回核实记录，没有完整取消就绪结果。新增后台只读 `GET /admin/orders/:id/cancellation-readiness`，返回：

```ts
{ orderId, orderRevision, observedAt,
  mode: 'PRE_DELIVERY_CANCEL' | 'POST_DELIVERY_RETURN' | 'TERMINAL',
  canCancel, steps, blockers, attention, actions,
  related: { review, terminationArchive, payments, refunds, tasks } }
```

- 与最终取消共用事实查询和判断函数，避免前端重复猜测或把交付 blockers 搬入取消页；GET 使用只读一致性事务，不改状态、版本、账单，也不查询或关闭渠道支付。
- 取消命令保留现有事务锁、当前员工/RBAC、版本、幂等以及最终全量实时核验。就绪结果只是当时的事实，不是跳过提交校验的授权。
- 动作白名单绑定本单、目标记录和正确版本（订单 revision、取消核实 revision、档案 revision 分开），权限不足显示负责岗位与原因，不暴露敏感材料。
- 管理员/运营办理取消核实与取消；相关档案继续独立复核；退款沿用财务及管理员权限和现有独立审批。合作商简化后的单人办理规则不外推到这些操作。
- 所有金额用整数分；资金判断逐笔校验，测试款也按真实已收款退款事实处理，不拿它抵租金。
- 正在进行的订单变更、车辆预留异常、渠道签署未结束、资料反馈未解决分别给出解释和真实入口。
- 当前取消命令并不强制先取消所有 FieldHandoverTask，也不会同步将这些任务全部取消。新 UI 不把“取消全部任务”发明成硬门槛；按已存在状态说明能撤销的安排。

## 7. 保留的交互与保护

- 按原页面保留刷新失败/409 后的输入，暂停提交，恢复完整当前数据后才可办理。
- “写入成功但读回失败”明确提示已写入，不诱导重复提交。返回关联资料保持本单、分区和位置。
- 主体切换不会清空用户正在编辑的材料，异步响应按订单和分区隔离；切到另一个订单不会沿用前单草稿。
- 文档原件在当前上下文中查看，可展开或单独阅读；大段协议不常驻操作区。
- 无权限入口不提供有效命令；最终命令仍服务器校验。显示禁用按钮时必须提供具体原因或下一步。

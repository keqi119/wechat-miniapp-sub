# 10月31日后台反馈修复设计

依据：用户本轮四项反馈及原需求，沿用已授权计划后直接施工。小程序生产发布继续暂停。

## 本轮行为

1. 合作商关联车辆只显示该合作商当前合作覆盖的车辆，与列表的合作车辆数使用相同范围。查询不能忽略合作商标识，错误/空结果不能回退全车。
2. 估值与折旧五种新增抽屉使用统一的固定头部、可滚动内容及可达操作区。新增操作为蓝色；草稿提交统一“保存草稿”；发布和最终确认用蓝色。保留原写入权限、版本冲突和幂等。
3. 复用现有 VehicleListing 多对一车辆结构，将每条车辆×产品版本的商品作为一个产品卡槽。在车辆商品展示中按车查看全部槽位、增加槽位、独立发布/下架。原商品列表提供按车管理入口。不设置固定槽位数，不能把全局单页分组伪装为该车全量。
4. 隐藏兼容套餐入口，新增商品只操作车辆和产品版本。内部既有兼容标识和历史申请/订单引用保留，禁止破坏性解绑或修改历史冻结条款。客户继续从真实车辆详情的多产品选择进入申请。
5. 产品适用车辆提供登记人、品牌、车型、年款、车龄范围、公里数范围、车牌、VIN筛选。查询覆盖完整台账；勾选保留筛选外选择，全选只追加当前筛选结果，取消该筛选结果不清除别处选择。最多1000台沿用产品契约；遇到失败/超限不提交半份选择。未知登记日期不推算车龄，年款不使用上牌年替代。
6. 车辆台账和详情显示真实所有人及登记信息，资料缺失明确未登记。用户已确认车辆所有人与车辆登记人均取机动车登记证所有人；合作商、牌照归属人另取各自事实，不互相冒充。保险信息、电池BaaS分两个页签，旧页签深链兼容。

## 边界与验证

- 所有私有查询继续后台RBAC和会话约束，不扩权到客户或合作商H5；字段白名单排除证件、协议原件、银行资料等。
- 同物理车辆的多商品保持原事务占用锁，不能形成两份有效占车；停用/下架商品禁止新申请，历史订单不变。
- 重要行为先写失败测试；接口筛选、记录隔离、选择保留和多商品申请是核心回归。抽屉用实际App合成数据浏览器检查1440与390布局及键盘操作。
- 在现有授权项目分支施工，已有未提交改动在 `.runtime/ninda/admin-feedback-20261031/before` 逐文件存档。只核本轮增量，不批量提交/推送。

用户本轮明确取消“保障要求”管理及相关流程控制。删除可操作入口及当前补核待办，不删除旧配置/审核/历史引用。保单草稿、提交、人工审批解除保障要求版本绑定；逐车审核真实保单附件，保留有效期、险种内容、被保车辆、独立复核、版本冲突、幂等。交车、换车目标交付和续期仍统一核验当时真实有效且已审保单，缺保单/过期/退保/移除车辆/无附件或无有效人工证据仍阻止办理。不因去掉配置而直接返回保障通过，亦不继续要求空配置永远失败。

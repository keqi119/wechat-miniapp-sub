## 3. 架构选择

推荐独立的模块化单体：一套 API 服务承载各业务模块，一套静态管理后台，一个独立 PostgreSQL 数据库。这个结构便于维护事务一致性，也适合已核查服务器的资源规模。

比较过的方向：

| 方向 | 评估 |
| --- | --- |
| 独立模块化 API + 静态管理后台 | 采用；覆盖小程序所需业务，部署和回滚集中管理 |
| 整体复制旧平台再裁剪 | 不采用；会带入不相关业务、历史迁移和旧前台假设 |
| 多个独立微服务 | 首发不采用；当前业务及服务器条件不需要增加服务间调用和运维成本 |

项目目录约定：

```text
reference/miniprogram-mock/  原样 Mock、配置和交付说明
apps/miniprogram/           真实小程序
apps/admin/                 React + TypeScript + Vite 管理后台
apps/api/                   NestJS + TypeScript API
packages/contracts/        接口约定、枚举和校验模型
deploy/                     独立容器、反向代理、部署与回滚配置
docs/                       方案、接口、操作手册、文案与验收证据
```

数据库采用 PostgreSQL，迁移由 Prisma 管理。依赖版本在施工时锁定并构建验证。后台风格沿用小程序的简洁配色与排版，以列表、筛选、详情和业务动作支撑日常运营。

客户 API 与管理 API 分区。后台采用安全会话和角色权限，小程序采用专用客户会话。鉴权后从服务端确定客户身份。异步通知、回调补偿和账单任务使用数据库任务记录、幂等键和并发控制；首发不为未证实的需要增加缓存服务。

## 4. 首发业务流程

```text
浏览车辆和预设套餐
→ 登录、完善资料、同意已发布协议
→ 提交申请
→ 后台审核资料、车辆、套餐与押金，必要时补件
→ 后台发布带版本号的最终方案
→ 客户确认或拒绝
→ 确认后创建正式待签约订单和方案快照
→ 电子签约
→ 支付押金和首期应付账单
→ 交接核对、独立交接单签署、后台确认交付
→ 用车、月度账单、权益、里程审核和服务工单
→ 退车结算及经审核的押金处理
```

- 申请提交只进入审核，不直接创建正式订单。
- 最终方案包含车辆、期限、月费、押金、里程、能源、权益、超里程条件及使用条件；确认需校验方案版本。
- 车辆占用与订单创建在事务中校验，防止同一车辆形成冲突订单；取消、过期和退车按状态规则释放。
- 费用以整数分存储。账单计划按最终方案及合同确认的起租日、付款日、月费生成，发布前由后台确认；演示日期不作为计费规则。
- 月度付款由客户主动发起，不包含自动续费代扣。额外费用和退车结算经后台审核后生成具体账单。
- 押金收入、使用、退回均留存独立记录。退款需由有权限的后台人员审核，通过支付渠道执行并核对最终结果。
- 真实款项到账以可信回调或渠道查询为准；客户页面返回、按钮点击和人工改前端状态不作为到账凭据。

- `submitMileage`：申报和审核读数分离，保留仪表照片与审核记录。

不存在记录、空列表、无权访问、会话失效、方案冲突、网络故障及供应商暂时异常分别处理。任何真实请求失败均显示相应状态，不返回演示成功数据。

已明确需要后续用户参与的事项集中在正式文案审定、平台账号验证/管理员确认，以及具体真实交易或签署验收；届时提供可审阅的文档、明确的平台动作或测试对象，不重复询问已确认的业务范围。

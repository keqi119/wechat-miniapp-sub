# 微信小程序交互参考

这是项目设计建议，不是对微信审核规则的复述。涉及平台 API、隐私授权或审核规范时，使用当前微信官方文档核对。

## 熟悉的结构

- 保持已有且有效的 tabBar 入口及语义；同一业务的二级内容放在页面内。详情页有清楚的返回目标，不另造一套网页导航。
- 用页面标题、分组标题和字段标签表达结构。装饰性英文不能替代中文任务名称。
- 原型预留微信胶囊与安全区；落地以平台真实尺寸和安全区信息为准，不把 iPhone 灵动岛、浏览器地址栏画进小程序。
- 主动作与次动作分级；破坏性动作单独表达。不可操作时说明原因与下一步责任方，不让客户猜“为什么灰了”。

## 内容决定排版

| 内容 | 优先呈现 | 避免 |
| --- | --- | --- |
| 多产品商品 | 车型、可选方案、月费构成、期限、押金、核心权益 | 只写低价起而不解释对应方案 |
| 账单 | 具体事由、所属服务期、应付/已付、明细与截止日 | 只写“订单支付”或用订单状态代替付款事实 |
| 流程 | 当前事实、谁来办、下一步动作、已完成时间 | 历史步骤永远阻塞或全部绿色 |
| 表单 | 常驻标签、示例格式、字段错误、保存结果 | 用 placeholder 代替标签、错误只靠颜色 |
| 记录/证据 | 时间、版本、来源、可查阅内容 | 已完成后仍要求重复勾选确认 |

## 交易和履约状态示例

以“证据提交 → 客户确认 → 平台核对实际完成”为例，三步是不同事实：

| 状态 | 客户页面 |
| --- | --- |
| 待客户确认 | 阅读证据与约定；未预选的同意项；确认/异议入口 |
| 客户已确认，平台待完成 | 显示本人确认时间、等待平台；隐藏再次确认控件 |
| 已完成 | 只读证据、确认和实际完成时间；保留记录查看 |
| 证据修订 | 指明新版本与变化；旧版本只读，新版本按业务要求重新确认 |
| 异议处理中 | 告知已收到异议及责任方，不误显示“已交付” |

支付页分别处理待支付、支付处理中、已支付、失败、退款中/已退款；支付成功不自动表示车辆已交付。授权、证件上传、人工审核、实名核验也分别表达。原型若没有接后端，动作只演示本地变化，并在原型外明确“演示”。

## 视觉起点与验证

建议正文 16px 左右、辅助信息 12–14px，数额与标题按层级放大；有效触控区域约 44px 起。它们是设计起点，遵循已有组件与适配结果。按 375px 设计稿换算 rpx 时，1px 对应 2rpx；实际布局保持弹性。

正文对比度以 4.5:1 为检查基线。浅黄适合做背景或与深色文字配对，不把黄色文字放白底；状态同时有文字，不能只靠红绿。先检查 320px、375/390px 和 430px，再核对真机字体与安全区。长中文、长金额、无图、空列表、加载、错误、禁用、成功和只读均按页面相关性覆盖，不强制给不相关组件凑齐状态。

静奢方案可以突出车图，但金额、条款和表单仍需稳定对比度；轻盈方案可以增加留白，但不能把每个字段拆成一张卡；原生方案可以紧凑，但主动作不挤进密集文字行。

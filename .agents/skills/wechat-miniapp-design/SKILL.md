# 微信小程序体验设计

让用户熟悉的操作路径承载品牌表达。参考 Huashu Design 的“先理解内容、以不同骨架比较方向、用实际画面验证”方法；这是一份针对微信小程序重新整理的技能，来源见 [sources.md](references/sources.md)。

## 先确定本次产物

从用户请求与已有上下文判断：风格提案、指定方向细化、现有页面修复，还是授权后的代码实现。用户要几套就提供几套；已选定方向时直接细化，不重新强制三选一。提案不意味着获准改动或发布正式应用。

复用已经明确的品牌、用户任务、页面路径、业务状态与素材。只对影响本次结果的缺口提问，能独立进行的工作继续。开发时读取项目约束和接口契约；视觉探索优先利用会话已有上下文，避免把提案扩大成全仓库审计。

## 产出可比较的设计

1. 固定比较内容：同一条业务任务、相同记录、价格、状态、屏幕宽度。示例内容明确标注；图片保留来源与许可，不把车型宣传照写成具体库存实拍。
2. 为每个方向写清：适合谁、第一眼看到什么、页面骨架、品牌色如何使用、实际取舍。至少在信息顺序、图文比例、分组方式或操作位置上形成有意义的区别，不能只换颜色和圆角。
3. 从本次授权范围内选择能检验方向的代表页。整应用提案可比较发现/选择、费用/账单、履约/记录；局部请求只取相关页面。提供可看的页面；需要判断流程时补局部可点击原型，不用形容词代替画面。
4. 保持微信习惯：沿用有效的一级导航，二级详情有明确返回，表单标签常驻，一个主要动作突出。具体状态、错误反馈、确认与完成态按参考文件处理。
5. 方案最终交付包含实际画面、简短推荐与取舍、可复用 token，以及尚未定稿的部分。用户选定或明确授权混搭后，把选择写入项目设计记录，再按授权范围推进。

## 核验与交接

按实际产物核验：检查窄屏和常见手机宽度、字体与对比度、底部安全区、长金额/长中文；实际打开渲染结果，操作主路径，确认没有溢出、遮挡、失效按钮或状态矛盾。浏览器原型通过不等于微信真机通过；代码落地还需开发者工具与真机验证。

实现时交付 token 与组件/页面映射，复用项目现有技术栈，不因视觉探索引入整套新框架。金额、权限、付款、签署、身份核验、幂等与流程判断继续由业务事实驱动，设计层不改写这些结果。

示例调用：`$wechat-miniapp-design 为现有车辆订阅小程序提供三种风格，比较选车、账单和已完成交接，先给可点击样稿。`
